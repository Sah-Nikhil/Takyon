# v0.4.5 Presentation

Make the Palette look like Raycast. A small phase, and deliberately gated: one
task ships, then it is judged on screen before the rest is decided.

**Status: tasks 1, 3 and 4 built.** Task 2 (section headers) remains **not
approved** and should not be built without a decision — the plan below carries
the reason it is the expensive one.

## Why this exists as a phase

Presentation was never on the ROADMAP. v0.5 is clipboard, v0.6 is settings, and
neither wants Palette chrome smuggled into it. This is its own phase so the
change has a plan, a verify script and screenshots like every other one, and so
v0.4 stays shippable and verified as it is.

## Read first

Raycast for Windows is the reference, from screenshots taken on this machine.
Four elements are visible in them and they are separable:

1. a large **calculator card** — expression, arrow, result, with labels beneath
2. **section headers** — Calculator / Results / Files
3. **right-aligned kind labels** on rows — "Application"
4. a **footer bar** — "Copy Answer ⏎ | Actions Ctrl K"

1, 3 and 4 are built. 2 is not approved.

## The constraint that shapes all of it

**The window is sized in Rust, from a row count.** `window::content_height`
computes `EMPTY_HEIGHT + rows × ROW_HEIGHT + LIST_CHROME`, mirrored by
`paletteHeight` in `packages/shared`, with a test asserting the two agree
(TBC-0006, ADR-0009). Every element above breaks the "every row is 44px"
assumption, so each one is a change to that arithmetic on both sides, not CSS.

Get it wrong in the cheap direction and the list grows a scrollbar when it fits;
get it wrong in the expensive direction and the last row is clipped by a
transparent, undecorated window. Neither is visible to the mocked visual layer,
because the mock has no window — a Rust unit test on the arithmetic is the only
thing that catches it.

## Tasks

### 1. The calculator card — **approved, built, green-lit**

Replace the Calc Entry's ordinary row with a card: the expression on the left,
an arrow, the result on the right, a label under each, and a small "Calculator"
caption above.

It stays a `Command.Item` inside the same list. That is the whole trick — the
card is a *rendering* of the selected entry, not a separate surface, so arrow
keys, Enter, `Ctrl+K` and the Stability rule keep working untouched and none of
`sources/calc` changes.

The caption is the one thing borrowed from task 2. It is part of what makes the
card read as Raycast's, and it labels exactly one thing rather than introducing
grouping. **Kept** — reviewed at green-light and left in.

Removing the row also removed two branches from `EntryRow` that a calculation can
no longer reach: the `=` placeholder glyph, and the opt-out from left-truncating
the second line. Both were v0.4 code that the card made dead.

### 2. Section headers — **not approved**

Grouped headers over the list: Calculator, Results, Files.

**This is the one with a real cost, and it is not layout.** Raycast groups by
category and ranks within a group. Takyon ranks everything into one list, which
is what all of v0.3 was: the tier ladder, Frecency lift, per-Kind weights and the
Stability rule.

`docs/tbd/v0.3.md` §10 records two live failures fixed by *removing* that kind of
boundary: `dis` returned the **Display** settings page above **Discord**, and
`disk` returned **Storage** above **Disk Cleanup**. The fix was making apps and
settings compete in one list with a 0.8 weight rather than gating one behind the
other. Sections put the gate back — Display sits in a lower section however often
it is used, because ranking can no longer promote across the boundary.

If this is wanted anyway, the honest version is **score-ordered sections**: group
for display, but order the groups by their best member's score rather than by a
fixed taxonomy. That keeps the ranker in charge and costs more than it looks.

### 3. Right-aligned kind labels — **approved, built**

"Application" on the right of each row, as in the screenshots.

Raised against [ADR-0016](../adr/0016-the-second-line-is-disambiguation.md)
before building: the second line is suppressed unless it disambiguates, and a
label on every row looks like exactly the decoration that rejected. Built anyway,
by decision, and **ADR-0016 is amended** with the distinction rather than left
contradicted: the second line answers "which of these two is which", the Kind
column answers "what will Enter do to this", and the second question has an
answer on every row.

A column, not a line — it costs no height and reflows nothing. `calc` has no
label because a calculation is a card.

### 4. The footer bar — **approved, built**

A strip along the bottom: what Enter does on the selected row, and `Ctrl+K` for
actions. Raycast's says "Copy Answer" against a calculation and "Open
Application" against an app.

The element that most improves discoverability: `actions::for_modifiers` has
been kind-aware since v0.4 and nothing in the UI said so. It replaced the `Ctrl K`
hint that used to float in the input row.

Labels come from `actions::all()`, fetched **once on mount** — an `invoke` per
arrow key would put IPC on the selection path, and shipping the strings with
every keystroke is what `Entry.actions` carrying ids instead of labels exists to
avoid. The footer reads the Entry's *first* action, which is the plain-Enter one
for every Kind; a Rust test pins that, because the shortcut is silently wrong the
day a Source reorders its actions.

`FOOTER_HEIGHT` is added in the same branch as the list, so an empty Palette has
no footer — there is no selected row to describe, and Raycast draws none either.

## Traps

**The mocked visual layer cannot see a wrong window height.** It renders in a
browser with no native window, so a card that overflows looks fine in Playwright
and clips in the product. The Rust arithmetic test is the guard; the screenshot
is not.

**A card is not a row, and `MAX_VISIBLE_ROWS` counts rows.** Eight rows plus a
card is taller than eight rows. The cap has to apply to what is left after the
card, or a query answering a calculation *and* eight apps grows past the shape
TBC-0006 chose.

**Do not let the card become a second surface.** The moment it stops being a
`Command.Item` it needs its own selection, its own key handling and its own
Stability behaviour, and the Palette grows a second way to do everything.

## Exit criteria

Task 1: a calculation reads as an answer rather than a list row, and the window
is exactly as tall as its content on a query that returns a calculation alone and
one that returns a calculation plus eight applications.
