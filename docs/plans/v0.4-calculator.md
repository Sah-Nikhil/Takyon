# v0.4 Calculator and converter

Second reflex after launching. Small phase.

> **Amended during the phase.** Three tasks below changed, each marked inline:
> task 1 (hand-rolled, not a crate), task 5 (currency deferred to v0.8), and the
> manual verification numbers. The amendments are the record of what shipped;
> the original wording is kept above each one so the change is visible rather
> than quietly rewritten.

## Read first

v0.3 done. ADR-0002 (Bangless never touches network). That ADR constrains
currency conversion specifically.

## Tasks, in order

1. **`sources/calc.rs`.** Inline expression evaluation. Arithmetic, parens,
   percent, exponent. ~~Pick a Rust expression crate rather than hand-rolling a
   parser.~~

   **Amended: hand-rolled, and it became `sources/calc/` — four files.**
   [TBC-0011](../tbc/0011-hand-rolled-expression-parser.md) carries the full
   reasoning and the trigger that would send us to a crate. The short version is
   that a crate covers `45+23 → 68` and nothing else this phase actually
   needed: the percent rule, the accept/reject policy, `40 kg to lb` and the `=`
   prefix are all ours either way, and they all want the same tokenizer.

   Layout: `expr.rs` (tokenizer, precedence-climbing parser, evaluator),
   `units.rs` (static tables), `fmt.rs` (rounding and grouping), `mod.rs`
   (policy and the `Source`). The split is deliberate — `expr.rs` is the only
   file a crate would ever replace.

2. **Detection.** Input that parses as an expression yields a Calc Entry at rank
   top. Input that does not parse yields nothing, silently. No error rows in a
   launcher.

   Built as specified, with the rules made explicit after watching Raycast on
   this machine (screenshots in the session that built this phase):
   - An unknown word is a hard parse error, never a variable. This one rule is
     what keeps `1password`, `x264` and `7zip` out of the calculator.
   - A trailing operator is refused. Raycast answers `45+` with 45; we do not,
     because the Stability rule already stops the top row flickering.
   - A **bare number answers only when formatting changes it** — `202` yields
     nothing, `2024` yields `2,024`. Raycast's rule, adopted knowingly, and its
     cost is in `docs/tbd/v0.4.md` §1.
   - A function name is only a function with `(` after it, so `log` stays a
     search for Logitech Options.

3. **Enter copies the result** to clipboard, Palette dismisses.

   Done, as a new `copy_answer` action. `actions::for_modifiers` became
   kind-aware: Enter against a Calc Entry copies rather than opening, which is
   what Raycast's footer says out loud ("Copy Answer", not "Open Application").
   The answer travels inside the EntryId, so activation needs no lookup — the
   Entry belongs to no index and there is nothing to look it up in.

4. **Unit conversion.** Length, mass, temperature, data, time. Static tables,
   fully offline.

   Done. Base unit per dimension rather than a table of pairs. Temperature is
   affine (`value * factor + offset`), which is the one case a factor-only table
   gets wrong everywhere except 0 °C. Data is 1024-based to match what File
   Explorer reports under the same "GB" label. Months and years are deliberately
   absent — neither has a fixed length, and inventing 30.44 days is precision we
   do not have.

5. ~~**Currency.** Needs live rates, so it leaves the machine. Bang-gated or
   explicitly opt-in with a default-off setting. Never on the Bangless path.~~

   **Amended: deferred to v0.8, and no currency code was written.**
   The plan offered two gates and v0.4 has neither: `bang.rs` does not exist
   until v0.8, and there is no settings store until v0.6 — `settings.rs` is a
   window shell, and the only preference in the product lives in the frontend's
   `localStorage`. Building a third mechanism to gate one feature, months before
   the real one lands, is how you end up with two settings stores.

   So there is no currency unit, no rate fetch and no cache. A unit test asserts
   that `usd`, `inr`, `eur` and friends resolve to nothing, which makes the
   ADR-0002 guarantee for this phase trivially checkable. `docs/tbd/v0.4.md` §2
   carries it with v0.8 as the owning phase.

6. **New: the `=` prefix and the Policy setting.** Not in the original plan.

   `=12*1.18` forces a calculation. It exists because the conservative rules in
   task 2 otherwise cost you the answers they decline, and because Raycast has
   no such key and is worse for it (typing `=45+23` there returns file results).

   Alongside it, a Settings switch chooses when the calculator may answer at all:

   | Policy | Behaviour |
   |---|---|
   | `automatic` (default) | Raycast's behaviour. Any unambiguous expression answers on the Bangless path. |
   | `explicit` | Only input starting with `=` is ever read as arithmetic. Nothing can take an application's top row. |

   **Not called a Mode.** `CONTEXT.md` reserves Mode for "the behaviour a Bang
   selects", and this is a setting rather than a Bang. It is not called a Trigger
   either — that word is on Bang's own *avoid* list.

   The Policy is enforced in Rust, on the keystroke path, so Rust holds it. The
   frontend remembers the choice in `localStorage` and pushes it across the seam
   on mount and on every show, exactly as `prefs.ts` already does for the motion
   switch. v0.6 moves both to `settings.db` together.

## Traps

**Currency is the ADR-0002 trap of this phase.** `100 usd to inr` on the Bangless
path is a network request, which breaks the product's central promise. Either put
it behind a Bang or behind an off-by-default setting. Not both, and never
neither.

*Outcome: neither gate existed yet, so the feature was not built. See task 5.*

Expression detection must be conservative. `1password` is not arithmetic. A
greedy parser turns app searches into calculator results.

*Outcome: this was the phase's real work, and it is worth being precise about
what "conservative" cost. The rule adopted is Raycast's, not a stricter one, so
`2022` does show `2,022` above "Adobe Photoshop 2022" and does take Enter from
it. That was chosen with the failure on screen. `explicit` is the way out, and
the Settings copy says so plainly.*

Cache currency rates with a visible timestamp. A stale rate presented as current
is worse than no rate.

*Carried to v0.8 unbuilt, along with the rest of currency.*

**New trap, found by a test rather than by review.** ADR-0016 strips the second
line from any row whose title is unique, which silently swallowed the expression
under every answer. The mocked visual layer could not see it — the mock does not
run the ranker — and the IPC contract test caught it. ADR-0016 is amended with a
Calc exemption; the reasoning is there.

## Exit criteria

You stop opening a calculator app. `12*1.18` and `40 kg to lb` both answer
inline, both offline.

## Manual verification

Superseded by [`docs/verify/v0.4.md`](../verify/v0.4.md), which carries these
four steps and the ones the amendments above added. Two numbers here were wrong
and are corrected there:

- step 2's `88.18 lb` is `88.1849 lb`. Four decimal places, not two — `fmt.rs`
  carries why, and throwing away two digits of a conversion someone asked for is
  not a rounding preference.
- step 4 no longer has a setting to turn off. Currency yields no result and no
  request because no currency unit exists.
