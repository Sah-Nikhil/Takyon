# The macOS clipboard: polled, marker-excluded, Keychain-wrapped

`clips::os::MacClipboard` implements `ClipboardStore` (ADR-0025) against
`NSPasteboard` directly. Three parts of ADR-0006 and ADR-0008 land differently on
macOS and each is stated here rather than discovered later.

## 1. There is no clipboard event, so it is polled

`watch.rs` rejected polling on Windows for a good reason: `AddClipboardFormatListener`
exists, and `GetClipboardSequenceNumber` polling "wakes a process whose whole
premise is being idle and warm" (ADR-0003).

**macOS ships no clipboard notification.** Apple provides no callback, no
notification, nothing. Every clipboard manager on the platform polls
`NSPasteboard.general.changeCount` — there is no alternative to reject polling in
favour of.

- **500 ms**, on a parked timer thread, not a spin loop. `changeCount` is a single
  integer read on an already-resident object.
- **Suspended entirely while the screen is locked or the display sleeps**, via
  `com.apple.screenIsLocked` / `com.apple.screenIsUnlocked` on
  `DistributedNotificationCenter`. This is not the "wrong sometimes" heuristic
  that ADR-0003 warns about: a locked machine cannot receive a user copy, so
  there is no case in which suspending loses one. It is what gives ADR-0003 an
  honest answer for the idle hours, which is where its premise actually lives.

Accepted cost: **two copies inside the same 500 ms window record as one.**

`pbcopy` and `pbpaste`, used as a stopgap before ADR-0026, are superseded. Once
the watcher needs `changeCount` anyway, spawning two processes per read buys
nothing.

## 2. The exclusion mechanism ports 1:1, and is slightly better

ADR-0006's primary safety mechanism is the clipboard format password managers set
to say "do not record this". macOS has a documented community convention, at
nspasteboard.org, that the same password managers implement:

| marker | meaning |
|---|---|
| `org.nspasteboard.ConcealedType` | confidential — do not record |
| `org.nspasteboard.TransientType` | transient — do not record |
| `org.nspasteboard.AutoGeneratedType` | the application wrote this; the user did not copy it |

`watch::EXCLUDE_FORMATS` maps straight across, and macOS gives three markers
where Windows gave two. **ADR-0006's headline safety story is fully intact**, and
it stays intact for image and file clips when those land, because a marker is a
property of the pasteboard rather than of the text.

## 3. Source attribution does not port, and the blocklist is best-effort

`NSPasteboard` has **no owner API**. There is no equivalent of
`GetClipboardOwner`, and `org.nspasteboard.source` is the wrong tool for this —
that convention is for a *history* application to stamp the original source when
it re-places old content, not for the originating application to identify itself.

So the second exclusion mechanism, the user's own executable blocklist, is
attributed by `NSWorkspace.frontmostApplication` at the moment `changeCount`
moved. That is right for every user-initiated copy and wrong for a background
process copying silently.

The blocklist is **kept and documented as best-effort on macOS**. Dropping it
would throw away a mechanism that works in the common case because it is not
perfect in the rare one — and the rare case is the one `AutoGeneratedType` is
designed to catch anyway.

## 4. The key lives in the Keychain, and that is stronger than DPAPI

`clips::key`'s DPAPI wrap becomes a Keychain generic password item, reached
through the **`security-framework`** crate (MIT/Apache — a genuinely new
dependency, one of only two in this port).

ADR-0008 described DPAPI's boundary as the user account, and its entropy argument
as "obfuscation rather than a boundary". A Keychain item with a default ACL is a
stronger claim: a process running *as the user* cannot read it without the
Keychain granting access. **macOS is therefore better protected than Windows
here, not equal**, and ADR-0008 should not be read as if the two were the same.

Rejected: the `security(1)` CLI, which puts secret material in an argv visible to
`ps`. Rejected: raw `SecItemAdd`/`SecItemCopyMatching` FFI, which is eighty lines
of `CFDictionary` construction whose error paths — locked keychain, denied ACL,
duplicate item — are exactly the ones nobody tests.

**ADR-0008's deletion rule still applies and gets harder.** `PRAGMA secure_delete`
plus `wal_checkpoint(TRUNCATE)` only covers what is inside SQLite. When image and
file clips arrive (`docs/plans/clipboard-kinds.md`), blob files must be
overwritten before unlinking — "the row is deleted" and "the secret is gone" are
different claims, and a file the OS never zeroes makes the gap wider.

## 5. Paste-back needs a permission that can only be asked for once

`CGEventPost` requires the Accessibility permission.
`AXIsProcessTrustedWithOptions` prompts **once per binary** — after a denial,
macOS never shows that prompt again and the call simply returns false.

So "ask every time until granted" cannot be a prompt. It is:

- One prompt on first launch, during onboarding.
- Thereafter, a **banner in the Palette** whenever paste-back is attempted without
  the permission, carrying a button that opens
  `x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility`
  directly.

`paste.rs`'s ordering rule is what makes this survivable: the clip is on the
clipboard before any keystroke is attempted, so a refused permission leaves the
user one manual `Cmd+V` away rather than with nothing.
