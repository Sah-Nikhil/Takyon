## 2. `code` reached the wrong application

**Fixed and confirmed 2026-08-25.** The ranking gap it exposed is v0.3's.

The plan's step 3 says `code` finds Visual Studio Code. Against the real binary it
found `code.cmd` — the `PATH` shim — and buried the editor four rows down. A bare
`PATH` entry was being given its basename as a *display name*, so it matched at
the exact-name rung (900) while the editor could only reach later-word (700). §3
puts executable basenames at 650 precisely so this cannot happen.

`Haystack::for_executable` now leaves the name empty. **Confirmed against the real
binary:** `code.cmd` dropped from first to last.

**What remains is a ranking gap, not a bug. Owner: v0.3.** `code` now returns
T3 Code (Alpha), then Visual Studio Code, then code-tunnel, then code.cmd.

Visual Studio Code is found but is not top. Both it and T3 Code match the word
"Code" at the later-word rung, and the only tiebreak without usage data is name
length — "t3 code (alpha)" is shorter. There is no principled text-only fix:
both are genuinely applications whose name contains "Code".

**This is the concrete case for v0.3.** Frecency is the missing signal, and this
is evidence rather than an assumption about what ranking needs.

## 3a. Fixed — `AppsFolder` was duplicating half its entries

**Closed 2026-08-25**, recorded because it moves the v0.3 baseline.

`appsfolder.rs` intends to skip Win32 apps, since `lnk.rs` finds them with a real
path. It did not: a Win32 app that registers an AUMID for taskbar pinning comes
back with an AUMID parsing name, which the "not a path" filter accepts. Visual
Studio Code and T3 Code each appeared **twice, with two different `EntryId`s**.

`SIGDN_FILESYSPATH` cannot separate them — an `AppsFolder` item is virtual, so it
fails for packaged and Win32 alike. The discriminator that works is the title: a
packaged entry whose name a Start Menu shortcut already produced is skipped, and
the Start Menu copy wins because it has a path, so it supports reveal, elevate
and copy.

**52 of 110 packaged entries were duplicates.** Total discovered went 1084 → 1032.
Every one of those 52 would have split its application's Frecency from v0.3.

## 4. The `AppsFolder` filter may be too strict

**Owner: v0.3.** Measure before widening.

`appsfolder::is_aumid` accepts anything that is not a path and not a shell GUID.
`WSL Settings` is dropped, because its parsing name is a KNOWNFOLDERID-relative
path:

```
{6D809377-6AF0-444B-8957-A3773F02200E}\WSL\wslsettings\wslsettings.exe
```

It contains backslashes, so the "not a path" test rejects it — correctly in the
narrow sense, but no other discovery path finds it either, so the app is invisible.

One entry on this machine. What is unknown is the size of the class: apps
registered through a known-folder-relative path are a real Windows pattern and
this filter sees none of them. **Count how many of the 189 `AppsFolder` items are
dropped and by which branch** before changing anything on the strength of one
example.

## 4a. Fixed — Windows stubs and aliases duplicating packaged apps

**Closed 2026-08-25.** Two mechanisms, because one signal does not cover both.

`C:\Windows\System32\calc.exe` and `notepad.exe` are stubs: run one and it exits
immediately, having started the packaged app that `AppsFolder` already lists under
its real name. **Verified by running them**, which is the only certain test —
nothing structural separates a stub from a real tool:

| Signal | Why it fails |
|---|---|
| File size | `notepad.exe` is 360 KB and a stub; `charmap.exe` is 282 KB and real |
| Sharing a name with a Store alias | that set is `bash, notepad, wsl, wslconfig` — it misses `calc`, and would wrongly take the WSL launchers |

So `SHIMS_TO_PACKAGED_APP` is a curated list, like `steam.rs`'s `NOT_GAMES`, and it
covers **the whole Windows directory** — `notepad.exe` ships in `C:\Windows` as well
as `System32`, both are on `PATH`, and checking only `System32` left the second copy
on screen.

The third copy was `%LOCALAPPDATA%\Microsoft\WindowsApps\notepad.exe`, a 0-byte App
Execution Alias. Those must not be filtered wholesale: `winget`, `wt`, `pwsh`,
`python` and `bash` are the only route to those tools. The safe rule is narrower —
**drop a `PATH` entry whose whole name matches an application already discovered**.
`notepad` collides with "Notepad"; `winget`, `wt` and `python` name no application,
so all survive. Confirmed against the real binary.

Also fixed here: `PATH` on this machine repeats the Windows directories **four
times** in two casings, so the walk read 627 files four times over. Directories are
now walked once, order preserved.

**Still open, deliberately:** `mspaint`, `SnippingTool` and `store` are aliases
whose packaged app has a differently-spelled title ("Paint", "Snipping Tool"), so
the name rule does not collapse them. Left alone — a fuzzier match would eventually
hide a real tool, and Frecency sorts it out. Revisit only if a week of use shows it
getting in the way.

## 7. Games installed through a launcher other than Steam are invisible

**Owner: v0.3** for the launcher sources. Extra app roots is a separate, weaker
idea — see below. Decided 2026-08-26 to defer both until v0.2 closes.

Raised 2026-08-26 from real use: `C:\GG\FitGirl\EA SPORTS FC 26\FC26.exe` never
appears for `fc26`, and Raycast finds it.

The first diagnosis in this entry was wrong and is corrected here, because the
wrong mechanism pointed at the wrong fix. Both are recorded — the mistake is the
useful part.

### What was checked, and what it ruled out

All four v0.2 Sources miss the game legitimately:

| Source | Why it misses |
|---|---|
| Start Menu `.lnk`, both roots | no shortcut exists — searched both trees, and the Desktop |
| `shell:AppsFolder` | not a packaged app |
| bare `.exe` on `PATH` | `C:\GG\FitGirl\` is not on `PATH` |
| Steam `.acf` | not a Steam game |

There is also no `Uninstall` and no `App Paths` registry entry, so the two
registry fallbacks other launchers reach for come up empty too.

### Wrong answer: a wide filesystem index

The first read of `%LOCALAPPDATA%\Raycast\index\` looked conclusive — a 46 MB
inverted index over 259,140 entries, and `grep` found "FitGirl" inside the `.dat`.
The conclusion drawn was that Raycast simply walks widely enough to reach `C:\GG`.

It does not. Raycast's own log prints its resolved scope:

```
user_paths:        ["C:\Users\<user>"]
exclude_patterns:  ["!**/AppData/**", "!**/[Cc]ache/**", "!**/[Cc]aches/**"]
max_walk_depth:    40
include_hidden_files: false
```

The index covers the user profile and nothing else. `C:\GG` is never walked.

Confirmed by byte search rather than by reading the config: across all four index
files, in UTF-8 and UTF-16LE, `C:\GG\FitGirl\EA SPORTS FC 26\FC26.exe` and the
bare prefix `C:\GG` each occur **zero** times. The single "fitgirl" hit in the
`.dat` is `WW2\MD5\fitgirl-bins_1.md5`, a checksum file from an unrelated repack
that does sit inside the user profile.

**The mistake was method, not luck.** A case-insensitive recursive `grep` for one
word matched a filename, and a substring match was taken as proof the executable
was indexed. The index's own scope was printed in Raycast's log the whole time and
was not read until later, while looking for something else. Grep proves a string is
present; it proves nothing about which string.

### Right answer: a game-launcher Source

Raycast discovers games from launcher metadata, as a distinct kind from apps:

```
[app-discovery] Added 8 launcher-managed game entries: Epic=7, Steam=0, GOG=0,
EA=1, Ubisoft=0, Blizzard=0, Riot=0, Battlestate=0, Rockstar=0, Roblox=0,
itch=0 in 1391ms
Indexing 181 App items
Indexing 15 Game items
```

Ten launchers, queried separately from applications. The repack registers itself
with EA Desktop — `C:\ProgramData\EA Desktop\InstallData\EA SPORTS FC 26\` exists
on this machine — so EA's own metadata reports it as installed, and Raycast
launches the executable directly (`CreateProcess … path=C:\GG\FitGirl\EA SPORTS
FC 26\FC26.exe`), not through a launcher URI.

**This is wider than one game.** `Epic=7` means seven Epic games are invisible in
Takyon today, and nobody had noticed because nobody searched for one. Steam is the
only launcher `sources/apps/` knows about, and on this machine Steam is the one
launcher with no games in it (§3).

### What would close it

**Epic first, and it is small.** The manifests are plain JSON, one file per game,
in `C:\ProgramData\Epic\EpicGamesLauncher\Data\Manifests\*.item`, with the three
fields that matter already spelled out:

```
DisplayName       = Dying Light
InstallLocation   = C:\GG\EpicLibrary/DyingLight
LaunchExecutable  = DyingLightGame.exe
```

Note the mixed separators — Epic writes them as they come, so the join has to
tolerate `/` inside a Windows path. Same shape as `steam.rs`, no new dependency,
and unlike Steam it can be tested here because seven games are installed. **It
also unblocks §3 indirectly:** the "a real game's name and id survive the round
trip" assertion finally has a game to make it with, even if `steam://rungameid/`
itself stays untested.

EA is messier. `InstallData\<name>\` gives the display name but the install path is
only in `EABackgroundService.log`, which is not a manifest and must not be parsed
as one. Leave EA until Epic proves the shape.

**Extra app roots** — a user-editable list of directories scanned for `.exe` at
index time — remains a reasonable feature, but it is no longer the answer to this
report. Prior art: Flow Launcher's Program plugin has it as **Custom Sources**,
alongside Start Menu, Registry and `PATH`, with filesystem watchers. PowerToys Run
does not; it is an open request,
[microsoft/PowerToys#37249](https://github.com/microsoft/PowerToys/issues/37249).
It is worth having for portable executables and unzipped tools. It is the wrong
tool for a game a launcher already knows the path of.

**v0.7's file search** would not have helped either, on the same evidence that
sank the first diagnosis: ADR-0007's defaults are Desktop, Documents, Downloads
and code directories, `C:\GG` is none of them, and a hit would be a file Entry
below applications with Bangless file results defaulting to off.

### Not being built yet, on purpose

Asked and answered 2026-08-26: v0.2 closes first. Starting either would open v0.3
on top of an unclosed phase. Extra app roots additionally has nowhere to store a
user-editable list — `settings.db` is v0.6, and today's only persistence is the
single boolean in `src/prefs.ts`. v0.3 hits that same wall for its user-defined
aliases, so that phase makes the storage decision anyway and roots should ride
along rather than force a mechanism v0.6 replaces. **The Epic source has no such
blocker** — it reads a fixed well-known path, exactly as `steam.rs` does, and
needs no settings at all.

Whenever roots are built, they need a depth cap and an exclusion rule before
shipping. A root of `C:\GG` is fine; a root of `C:\` is not, and the 20 ms
`SOURCE_BUDGET` does not help at index time.

**Workaround until then, no code:** create a Start Menu shortcut to the
executable, working directory set to the game folder (repacks load data relative
to cwd). `lnk.rs` picks it up on the next index.

### Second finding: ADR-0007's throughput number has moved

ADR-0007 cites this machine's Raycast at **288,592 entries in 24.7 s** (~11,700/s)
as evidence that a directory walk is fast enough to make a LocalSystem service
unnecessary. The same file today reads **259,140 entries in 54.75 s** (~4,733/s):
fewer entries, 2.2x the time, one generation, one spawn attempt.

The decision is unaffected — 54.75 s still sits inside v0.7's "under 60 s in the
background" exit criterion, and a service is still a permanent cost against a
one-time one. But the margin is far thinner than the ADR implies, and the walk
budget should be planned against ~4,700 entries/s rather than ~11,700. Worth a
measurement note on the ADR; not worth reopening it.

## Not open — recorded to prevent re-litigation

These are decisions, not gaps. They are here so nobody reopens them as if they
were oversights.

- **The Entry list is not virtualised.** §3 caps the ranker at 12 Entries and 8 are
  on screen, so the worst case is 12 rendered rows; a windowing library would add
  a dependency and a measurement pass to avoid four `<div>`s. Revisit when a Source
  returns an unbounded set — v0.7's file search is the candidate.
- **No application cache on disk.** ADR-0012, with the measured walk time and the
  trigger that would change it.
- **Modifier accelerators are not user-rebindable yet.** The table is data in
  `actions.rs`; the UI that edits it needs `settings.db` and is v0.6.
