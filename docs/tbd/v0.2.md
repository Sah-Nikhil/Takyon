## 2. `code` reached the wrong application

**Fixed and confirmed 2026-08-25.** The ranking gap it exposed is v0.3's.

The plan's step 3 says `code` finds Visual Studio Code. Against the real binary it
found `code.cmd` — the `PATH` shim — and buried the editor four rows down. A bare
`PATH` entry was being given its basename as a *display name*, so it matched at
the exact-name rung (900) while the editor could only reach later-word (700). §3
puts executable basenames at 650 precisely so this cannot happen.

`Haystack::for_executable` now leaves the name empty. **Confirmed against the real
binary:** `code.cmd` dropped from first to last.

**What remains is a ranking gap, not a bug. Owner: v0.3.** `code` now returns
T3 Code (Alpha), then Visual Studio Code, then code-tunnel, then code.cmd.

Visual Studio Code is found but is not top. Both it and T3 Code match the word
"Code" at the later-word rung, and the only tiebreak without usage data is name
length — "t3 code (alpha)" is shorter. There is no principled text-only fix:
both are genuinely applications whose name contains "Code".

**This is the concrete case for v0.3.** Frecency is the missing signal, and this
is evidence rather than an assumption about what ranking needs.

## 3a. Fixed — `AppsFolder` was duplicating half its entries

**Closed 2026-08-25**, recorded because it moves the v0.3 baseline.

`appsfolder.rs` intends to skip Win32 apps, since `lnk.rs` finds them with a real
path. It did not: a Win32 app that registers an AUMID for taskbar pinning comes
back with an AUMID parsing name, which the "not a path" filter accepts. Visual
Studio Code and T3 Code each appeared **twice, with two different `EntryId`s**.

`SIGDN_FILESYSPATH` cannot separate them — an `AppsFolder` item is virtual, so it
fails for packaged and Win32 alike. The discriminator that works is the title: a
packaged entry whose name a Start Menu shortcut already produced is skipped, and
the Start Menu copy wins because it has a path, so it supports reveal, elevate
and copy.

**52 of 110 packaged entries were duplicates.** Total discovered went 1084 → 1032.
Every one of those 52 would have split its application's Frecency from v0.3.

## 4. The `AppsFolder` filter may be too strict

**Owner: v0.3.** Measure before widening.

`appsfolder::is_aumid` accepts anything that is not a path and not a shell GUID.
`WSL Settings` is dropped, because its parsing name is a KNOWNFOLDERID-relative
path:

```
{6D809377-6AF0-444B-8957-A3773F02200E}\WSL\wslsettings\wslsettings.exe
```

It contains backslashes, so the "not a path" test rejects it — correctly in the
narrow sense, but no other discovery path finds it either, so the app is invisible.

One entry on this machine. What is unknown is the size of the class: apps
registered through a known-folder-relative path are a real Windows pattern and
this filter sees none of them. **Count how many of the 189 `AppsFolder` items are
dropped and by which branch** before changing anything on the strength of one
example.

## 4a. Fixed — Windows stubs and aliases duplicating packaged apps

**Closed 2026-08-25.** Two mechanisms, because one signal does not cover both.

`C:\Windows\System32\calc.exe` and `notepad.exe` are stubs: run one and it exits
immediately, having started the packaged app that `AppsFolder` already lists under
its real name. **Verified by running them**, which is the only certain test —
nothing structural separates a stub from a real tool:

| Signal | Why it fails |
|---|---|
| File size | `notepad.exe` is 360 KB and a stub; `charmap.exe` is 282 KB and real |
| Sharing a name with a Store alias | that set is `bash, notepad, wsl, wslconfig` — it misses `calc`, and would wrongly take the WSL launchers |

So `SHIMS_TO_PACKAGED_APP` is a curated list, like `steam.rs`'s `NOT_GAMES`, and it
covers **the whole Windows directory** — `notepad.exe` ships in `C:\Windows` as well
as `System32`, both are on `PATH`, and checking only `System32` left the second copy
on screen.

The third copy was `%LOCALAPPDATA%\Microsoft\WindowsApps\notepad.exe`, a 0-byte App
Execution Alias. Those must not be filtered wholesale: `winget`, `wt`, `pwsh`,
`python` and `bash` are the only route to those tools. The safe rule is narrower —
**drop a `PATH` entry whose whole name matches an application already discovered**.
`notepad` collides with "Notepad"; `winget`, `wt` and `python` name no application,
so all survive. Confirmed against the real binary.

Also fixed here: `PATH` on this machine repeats the Windows directories **four
times** in two casings, so the walk read 627 files four times over. Directories are
now walked once, order preserved.

**Still open, deliberately:** `mspaint`, `SnippingTool` and `store` are aliases
whose packaged app has a differently-spelled title ("Paint", "Snipping Tool"), so
the name rule does not collapse them. Left alone — a fuzzier match would eventually
hide a real tool, and Frecency sorts it out. Revisit only if a week of use shows it
getting in the way.

## Not open — recorded to prevent re-litigation

These are decisions, not gaps. They are here so nobody reopens them as if they
were oversights.

- **The Entry list is not virtualised.** §3 caps the ranker at 12 Entries and 8 are
  on screen, so the worst case is 12 rendered rows; a windowing library would add
  a dependency and a measurement pass to avoid four `<div>`s. Revisit when a Source
  returns an unbounded set — v0.7's file search is the candidate.
- **No application cache on disk.** ADR-0012, with the measured walk time and the
  trigger that would change it.
- **Modifier accelerators are not user-rebindable yet.** The table is data in
  `actions.rs`; the UI that edits it needs `settings.db` and is v0.6.
