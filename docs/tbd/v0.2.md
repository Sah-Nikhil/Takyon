## 3a. Fixed — `AppsFolder` was duplicating half its entries

**Closed 2026-08-25**, recorded because it moves the v0.3 baseline. The rule it
settled is ADR-0014; this section is the evidence, not the decision.

`appsfolder.rs` intends to skip Win32 apps, since `lnk.rs` finds them with a real
path. It did not: a Win32 app that registers an AUMID for taskbar pinning comes
back with an AUMID parsing name, which the "not a path" filter accepts. Visual
Studio Code and T3 Code each appeared **twice, with two different `EntryId`s**.

`SIGDN_FILESYSPATH` cannot separate them — an `AppsFolder` item is virtual, so it
fails for packaged and Win32 alike. The discriminator that works is the title: a
packaged entry whose name a Start Menu shortcut already produced is skipped, and
the Start Menu copy wins because it has a path, so it supports reveal, elevate
and copy.

**52 of 110 packaged entries were duplicates.** Total discovered went 1084 → 1032.
Every one of those 52 would have split its application's Frecency from v0.3.

## 4. The `AppsFolder` filter may be too strict

**Owner: v0.3.** Measure before widening.

`appsfolder::is_aumid` accepts anything that is not a path and not a shell GUID.
`WSL Settings` is dropped, because its parsing name is a KNOWNFOLDERID-relative
path:

```
{6D809377-6AF0-444B-8957-A3773F02200E}\WSL\wslsettings\wslsettings.exe
```

It contains backslashes, so the "not a path" test rejects it — correctly in the
narrow sense, but no other discovery path finds it either, so the app is invisible.

One entry on this machine. What is unknown is the size of the class: apps
registered through a known-folder-relative path are a real Windows pattern and
this filter sees none of them. **Count how many of the 189 `AppsFolder` items are
dropped and by which branch** before changing anything on the strength of one
example.

### Measured 2026-08-27, during v0.3 task 0

**189 items: 112 accepted, 77 dropped, all 77 by the same branch** — a path
separator. The `shell:`/`::{` branch fires on nothing at all, so the shell-GUID
test is currently dead weight rather than a filter.

`WSL Settings` is not special. The 77 break down as:

| Shape | Count | Example | Wanted? |
|---|---|---|---|
| `{KNOWNFOLDERID}\...` | ~48 | `{6D809377-…}\WSL\wslsettings\wslsettings.exe` | some |
| Absolute path | ~17 | `C:\GG\STEAM\steam.exe` | already found by `lnk.rs` |
| `http://`, `https://` | 6 | `https://nodejs.org/` | no — correctly dropped |
| Docs and data files | ~6 | `…\WinRAR\WinRAR.chm`, `…\Git\ReleaseNotes.html` | no |

So the class is real and roughly 48 strong, but most of it is already on screen
from another Source, and the part that is not comes with `.chm`, `.html` and
`.url` files attached. Widening `is_aumid` to accept a `{GUID}\`-relative parsing
name would need the noise rule extended to file extensions first — and every one
of those items is reached by AUMID, so it would arrive with Open as its only
action while `lnk.rs`'s copy has the full menu.

**Verdict: not widened.** The measurement is here so the next person weighs 48
against those costs rather than re-running the count. Still open, still v0.3's if
it is taken; unchanged from one example to a measured class.

## 4a. Fixed — Windows stubs and aliases duplicating packaged apps

**Closed 2026-08-25.** Two mechanisms, because one signal does not cover both.
The collision policy behind it is ADR-0014.

`C:\Windows\System32\calc.exe` and `notepad.exe` are stubs: run one and it exits
immediately, having started the packaged app that `AppsFolder` already lists under
its real name. **Verified by running them**, which is the only certain test —
nothing structural separates a stub from a real tool:

| Signal | Why it fails |
|---|---|
| File size | `notepad.exe` is 360 KB and a stub; `charmap.exe` is 282 KB and real |
| Sharing a name with a Store alias | that set is `bash, notepad, wsl, wslconfig` — it misses `calc`, and would wrongly take the WSL launchers |

So `SHIMS_TO_PACKAGED_APP` is a curated list, like `steam.rs`'s `NOT_GAMES`, and it
covers **the whole Windows directory** — `notepad.exe` ships in `C:\Windows` as well
as `System32`, both are on `PATH`, and checking only `System32` left the second copy
on screen.

The third copy was `%LOCALAPPDATA%\Microsoft\WindowsApps\notepad.exe`, a 0-byte App
Execution Alias. Those must not be filtered wholesale: `winget`, `wt`, `pwsh`,
`python` and `bash` are the only route to those tools. The safe rule is narrower —
**drop a `PATH` entry whose whole name matches an application already discovered**.
`notepad` collides with "Notepad"; `winget`, `wt` and `python` name no application,
so all survive. Confirmed against the real binary.

Also fixed here: `PATH` on this machine repeats the Windows directories **four
times** in two casings, so the walk read 627 files four times over. Directories are
now walked once, order preserved.

**Still open, deliberately:** `mspaint`, `SnippingTool` and `store` are aliases
whose packaged app has a differently-spelled title ("Paint", "Snipping Tool"), so
the name rule does not collapse them. Left alone — a fuzzier match would eventually
hide a real tool, and Frecency sorts it out. Revisit only if a week of use shows it
getting in the way.

## 7. Coverage gaps found by comparing against Raycast

**Owner: v0.3.** Planned, not outstanding — see
[`../plans/v0.3-ranking.md`](../plans/v0.3-ranking.md) tasks 8–10 and the ROADMAP
entry. This section keeps only the evidence and the reasoning error, because
neither belongs in a build plan.

Raised 2026-08-26 from real use: `C:\GG\FitGirl\EA SPORTS FC 26\FC26.exe` never
appears for `fc26`, and Raycast finds it.

### The first diagnosis was wrong

`%LOCALAPPDATA%\Raycast\index\` holds a 46 MB inverted index over 259,140 entries,
and a recursive `grep -i` for "FitGirl" matched inside its `.dat`. The conclusion
drawn was that Raycast walks widely enough to reach `C:\GG`.

It does not. Raycast's own log prints its resolved scope:

```
user_paths:        ["C:\Users\<user>"]
exclude_patterns:  ["!**/AppData/**", "!**/[Cc]ache/**", "!**/[Cc]aches/**"]
max_walk_depth:    40
search_paths:      []
```

Confirmed by byte search rather than by reading the config: across all four index
files, in UTF-8 and UTF-16LE, `C:\GG\FitGirl\EA SPORTS FC 26\FC26.exe` and the
bare prefix `C:\GG` each occur **zero** times. The single "fitgirl" hit is
`WW2\MD5\fitgirl-bins_1.md5`, a checksum file from an unrelated repack that does
sit inside the user profile.

**The mistake was method, not luck.** A case-insensitive grep for one word matched
a filename, and a substring match was taken as proof the executable was indexed.
The index's own scope was printed in the log the whole time and was not read until
later, while looking for something else. Grep proves a string is present; it
proves nothing about *which* string. Recorded because the wrong mechanism pointed
at the wrong fix — a filesystem index, which would not have helped.

### What actually finds it, and what else that exposed

Raycast discovers games from launcher metadata, as a kind distinct from apps. Its
full app-side discovery on this machine, from its log:

| Source | Count | Takyon |
|---|---|---|
| Start Menu shortcuts | 156 from 184 files | yes |
| MSIX / Store | 36 | yes |
| `PATH` executables | not logged | yes — Takyon may be broader here |
| winget | 4 | no — v0.3 task 10, measure first |
| Launcher-managed games | 8 (Epic 7, EA 1, of 10 launchers) | Steam only — v0.3 task 9 |
| Control panel items and tasks | 234 | no — v0.3 task 8 |
| Windows settings catalog | 947 | no — v0.3 task 8 |
| **Prepopulated total** | **1383** → 181 App + 15 Game + 1187 Preference | |

Takyon finds 1032 applications. Raycast finds 181 apps and 1187 *preferences* —
a different product decision, not a bigger number. **The settings and control
panel entries are the largest gap**, and they were not in ROADMAP at any phase
until this comparison; that is a hole in the plan rather than work left undone.

### Two claims made here that were also wrong

Both were checked afterwards and corrected, because a plan was about to be built
on them:

- **"Seven Epic games are invisible in Takyon today."** They are not installed.
  All seven `InstallLocation` directories exist but are empty, and `NBA2K21`'s is
  gone entirely. Epic does not remove a manifest when the files go, and Raycast
  lists all seven as launchable. A correct Epic Source — one that existence-checks,
  per ADR-0013 — returns **zero** Entries here. Takyon showing nothing is right;
  Raycast showing seven dead rows is the bug.
- **"EA is the messier one, leave it until Epic proves the shape."** True, but for
  a stronger reason than assumed. EA has no structured record of the install path
  at all: `InstallData\<name>\` gives only the display name, `machine.ini` carries
  `machine.downloadinplacedir` (the download directory, not the install), and the
  real path appears only in `EABackgroundService.log`. A log is not a manifest.

The practical consequence is that **EA is the one launcher with a live game on
this machine, and it is the one that cannot be read** — so the game that raised
this report stays unreachable even after v0.3 task 9 ships. Prior art does not
help: Raycast reads it, but from something not found here.

**Workaround, no code:** a Start Menu shortcut to the executable, working
directory set to the game folder (repacks load data relative to cwd). `lnk.rs`
picks it up on the next index.

### Second finding: ADR-0007's throughput number has moved

ADR-0007 cites this machine's Raycast at **288,592 entries in 24.7 s**
(~11,700/s) as evidence that a directory walk is fast enough to make a
LocalSystem service unnecessary. The same file today reads **259,140 entries in
54.75 s** (~4,733/s): fewer entries, 2.2× the time, one generation, one spawn
attempt.

The decision is unaffected — 54.75 s still sits inside v0.7's "under 60 s in the
background" exit criterion, and a service is still a permanent cost against a
one-time one. But the margin is far thinner than the ADR implies, and the walk
should be budgeted against ~4,700 entries/s. Worth a measurement note on the ADR;
not worth reopening it.

Raised 2026-08-26: `C:\Applications\Productivity\Creative\ADOBE\Adobe Premiere
Pro 2022\Adobe Premiere Pro.exe` appears in no launcher — not Takyon, not the
Start menu, not Raycast.

### Nothing on the machine says it is an application

| Signal | Present |
|---|---|
| Start Menu shortcut | no |
| Desktop shortcut | no |
| `App Paths` registry | no |
| `Uninstall` registry | no |
| Raycast file index | no — scope is `C:\Users\<user>` only |
| Raycast app discovery | no — Start Menu / MSIX / winget / launchers |

Raycast does not miss this by accident. There is no metadata to find. The only
evidence that the file is an application is that it is an `.exe` in a folder named
after itself, under a tree the *user* thinks of as applications. **This is the one
case that genuinely requires a user-declared root** — unlike §7's game, which had
launcher metadata all along.

### Why a root cannot simply take every `.exe`

Measured under `C:\Applications`:

```
179  .exe files across 18 app folders
 19  survive a crude name-matches-folder rule
 ~9  are actually launchable
```

Android Studio alone contributes `java.exe`, `jar.exe`, `jarsigner.exe`,
`fsnotifier.exe`, `elevator.exe`, `restarter.exe` and the rest of its bundled JBR.
Photoshop and Premiere each ship a `CEPHtmlEngine.exe`. There is an `ngrok.exe`
seven levels down inside `node_modules`. Even the crude rule above still admits
`CEPHtmlEngine`, `tailscaled` and `win-askpass`.

**20:1 noise.** A root that adds 179 rows to a 1032-app corpus makes the Palette
worse even with Frecency behind it. So the feature is not "walk and take every
`.exe`" — it is a shape rule (depth cap, name-matches-folder, exclusions for
`uninstall`/`unins000` and `jbr`/`jre`/`lib`/`node_modules`), and **that rule is
the work**, not the walk. Prior art: Flow Launcher's Program plugin ships this as
Custom Sources with file-type and depth settings; PowerToys Run does not have it
at all ([#37249](https://github.com/microsoft/PowerToys/issues/37249)); Raycast's
file indexer exposes a `search_paths` list, empty on this machine.

It also needs somewhere to store a user-editable list, and `settings.db` is v0.6.

### `App Paths`: a declared list Takyon does not read

`HKLM`/`HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths` is the key
behind Win+R. Each subkey is an executable name; its default value is the full
path. Installers write it to make an app runnable by name without putting its
folder on `PATH`.

**58 entries on this machine, 55 resolving to a real file.** It reaches
applications no other Source does:

```
zen.exe      C:\ZenBrowser\zen.exe
code.exe     C:\Applications\Productivity\Code\IDE\Microsoft VS Code\Code.exe
WinRAR.exe   C:\Applications\Productivity\Misc\WinRAR\WinRAR.exe
AfterFX.exe  C:\ADOBE\Adobe After Effects 2022\Support Files\AfterFX.exe
```

One registry enumeration, no walking, and the paths are declared rather than
guessed — far higher precision than a root scan. Two caveats: 3 of 58 point at
files that are gone, so it needs `lnk.rs`'s existence check; and roughly half are
helper processes rather than applications (`sdxhelper`, `msoadfsb`,
`licensemanagershellext`, `PAD.ChildSession.Service.Host`), so it needs a noise
rule of its own.

**It does not contain Premiere.** It solves a different set of missing apps.

### What each of the three actually fixes

| | Finds Premiere | Cost | Status |
|---|---|---|---|
| Desktop shortcuts | no | hours, reuses `lnk.rs` | **v0.3 task 11** |
| `App Paths` | no | small, needs a noise rule | undecided |
| Extra app roots | **yes** | shape rule + settings storage | undecided |

Only the third reaches it, and it is the most expensive. Recorded so the ordering
is not rediscovered: the two cheap wins do not close this report, and shipping
them must not be mistaken for having done so.

**Workaround, no code:** a Start Menu or Desktop shortcut to the executable.
Either is picked up on the next index once task 11 lands.

## Not open — recorded to prevent re-litigation

These are decisions, not gaps. They are here so nobody reopens them as if they
were oversights.

- **The Entry list is not virtualised.** §3 caps the ranker at 12 Entries and 8 are
  on screen, so the worst case is 12 rendered rows; a windowing library would add
  a dependency and a measurement pass to avoid four `<div>`s. Revisit when a Source
  returns an unbounded set — v0.7's file search is the candidate.
- **No application cache on disk.** ADR-0012, with the measured walk time and the

- **Modifier accelerators are not user-rebindable yet.** The table is data in
  `actions.rs`; the UI that edits it needs `settings.db` and is v0.6.

## 9. ~~One executable, many applications: the identity collision that hides 15 of them~~

**Closed 2026-08-27 by v0.3 task 0.** Kept in full because it is the evidence
behind [ADR-0014](../adr/0014-durable-identity-wins-a-collision.md)'s amendment
and because two of its three consequences were separate fixes.

What landed:

- **Arguments join `EntryId`** where a shortcut has them, joined by `|`, with the
  argument-free case byte-identical. Confirmed against the real walk: 34
  argument-bearing ids, thirteen of them across the three host binaries named
  below, and the nine `cmd.exe` applications are now nine Entries.
- **`Store app` is detected, not asserted.** `appsfolder::is_packaged` tests the
  package family name — `<name>_<publisher>!<appid>`, publisher id 13 lowercase
  alphanumerics. Measured on this machine: **112 accepted AUMIDs, 38 packaged, 74
  Win32**, every one of which v0.2 subtitled `Store app`. Not "contains a `!`":
  `Start ADB Server` is `664~fWx6w8A2!1wg'A4D>(FpPBCfr_+uUuDiMG4YH` and is not
  packaged.
- **`is_noise` moved to `sources/apps/noise.rs`** and now runs on the
  `AppsFolder` path too, which is how "Uninstall Node.js" was reaching the
  Palette after the `.lnk` walk had dropped it.

Not closed here, and deliberately: the **action menu** for a Win32 `AppsFolder`
entry is still Open alone. That was right all along — the row is reached by AUMID
and has no path to reveal, elevate or copy. The 15 that had files now come back
through `lnk.rs` with their real paths and the full menu.

The **six shortcuts with no target path are four**, and none of them is lost.
Re-measured 2026-08-27: 153 `.lnk` today against 155 then, and Clash of Clans and
Hungry Shark are gone from the machine. The remaining four are all reachable
through `AppsFolder` and always were — `Microsoft.Windows.Explorer`,
`Microsoft.Windows.ControlPanel`, `Microsoft.Windows.Shell.RunDialog` and
`CNEventWindowClass` for AMD Software: Adrenalin Edition. The defect was never
that they were missing; it was that all four were labelled `Store app`, which the
detection above fixes. No new `LaunchTarget` was needed and none was added.

---

### Original report

[ADR-0014](../adr/0014-durable-identity-wins-a-collision.md)
makes `EntryId` the Frecency key from v0.3. This section is the case that ADR did
not anticipate, and writing Frecency on top of it would teach the ranker the wrong
thing on the first day.

`EntryId::for_launch` maps a `LaunchTarget::Exe` to its lowercased path and
deliberately ignores arguments — there is a test named
`v0_2_launch_arguments_do_not_change_identity` asserting exactly that. The
reasoning was sound for the case it was written against: two shortcuts to one
application with different switches are one application.

It is wrong for a **host binary**. On this machine nine Start Menu shortcuts point
at `cmd.exe`, three at `javacpl.exe`, three at the x86 `powershell.exe`. They are
not one application with nine sets of switches; the arguments *are* the
application. `discover_all`'s `seen.insert(app.id)` therefore keeps whichever one
the walk reached first and silently drops the rest.

Measured on the development machine, 2026-08-27, across both Start Menu roots:

| | Count |
|---|---|
| Start Menu `.lnk` files | 155 |
| Distinctly-named applications lost to a shared target | **15** |
| Shortcuts with **no** target path at all, dropped outright | 6 |

The 15:

| Target | Applications collapsed into one |
|---|---|
| `cmd.exe` | Command Prompt, Developer Command Prompt for VS 2022, x64 Native Tools, x86 Native Tools, x64_x86 Cross Tools, x86_x64 Cross Tools, KiCad 8.0 Command Prompt, Node.js command prompt, Install Additional Tools for Node.js |
| `javacpl.exe` | About Java, Check For Updates, Configure Java |
| `powershell.exe` (SysWOW64) | Windows PowerShell (x86), Debuggable Package Manager, Developer PowerShell for VS 2022 |
| `EALauncher.exe` | EA, App Recovery |
| `onenote.exe` | OneNote, Sticky Notes (new) |
| `wsl.ico` | WSL, WSL Settings |

The six with no target: File Explorer, Control Panel, Run, AMD Software: Adrenalin
Edition, Clash of Clans, Hungry Shark Evolution. `com::read` returns a raw path and
checks it exists (ADR-0013); a shortcut to a CLSID or a shell folder has no path to
return.

### Why this did not look like a bug

Because most of them come back. `AppsFolder` mirrors Win32 applications that
register an AUMID, and `discover_all` step 2 skips an AppsFolder item only when a
Start Menu Entry already carries that **title** — which these do not, because they
were dropped. So they reappear as `LaunchTarget::Aumid`, and three things follow:

1. **They are subtitled `Store app`.** That string is asserted unconditionally at
   `sources/apps.rs:264`, never detected. Verified in the Palette: `developer`
   returns "Developer PowerShell for VS 2022 — Store app" and "Developer Command
   Prompt for VS 2022 — Store app"; `explorer` returns "File Explorer — Store app".
   None is a packaged application.
2. **Their action menu is truncated to Open**, because `actions.rs` keys off
   `LaunchTarget::Aumid` meaning "no file". These have files. E8's rule is being
   applied to things it was not written about.
3. **`is_noise` is bypassed.** It runs in `lnk.rs` only. "Uninstall Node.js" is
   dropped from the `.lnk` walk and returns through `AppsFolder`, subtitled
   `Store app`, above real applications for the query `node`. The filter that
   exists so `chr` does not offer "Uninstall Chrome" does not cover the path that
   actually produced the row.

One more consequence, visible in the Palette: `explorer` returns **"Windows
Software Development Kit"** subtitled `C:\WINDOWS\explorer.exe`. A folder shortcut
in the SDK's Start Menu group won the `explorer.exe` identity, so the row that
opens File Explorer is named after the SDK.

### What would close it

Identity has to include whatever distinguishes two shortcuts to one host binary.
The cheapest correct answer is to fold the arguments into the id **when they
exist**, leaving the argument-free case byte-identical so nothing already learned
is invalidated. That contradicts `v0_2_launch_arguments_do_not_change_identity`,
so the test and ADR-0014 both need amending in the same change rather than the
test being quietly deleted.

Shortcuts with no target path need a second question rather than a fix here: a
CLSID shortcut is launchable through the shell even though it has no path, and
`ShellExecuteW` on the `.lnk` itself would start every one of the six.

## 10. ~~`icons.bin` has never held an icon~~

**Closed 2026-08-27 by v0.3 task 0.**

The single post-walk `flush()` is gone. That thread now loops on a
**750 ms debounce** — `icons::should_flush(pending, idle)` is true once something
has been extracted and extraction has stopped — so the blob is written after the
icons exist rather than before. `flush()` also returns early when nothing is
pending, so it can no longer write the 12-byte header on its own; that is
`v0_3_a_flush_with_nothing_extracted_writes_no_blob`, which fails against the
v0.2 code.

Up to 750 ms of extraction is lost if the process is killed rather than quit.
That costs a re-extraction of those icons and nothing else.

The sentence this invalidated — ROADMAP v0.2's "the expensive half is already
persisted in `icons.bin`" — is true from here on.

---

### Original report

`flush()` is called from exactly one place — `lib.rs:275`, immediately after
`apps.refresh(&icons)` — and its comment says it persists "whatever the pre-warm
extracted". There is no pre-warm. `refresh` calls `icons.register(...)`, which only
records *where* an icon could be extracted from; extraction happens lazily in
`IconStore::get`, called from the `takyon-icon://` protocol handler when a row is
actually drawn. At flush time `ready` is therefore always empty.

So the file is written once per launch, containing `TKI1`, format version 1, and a
count of **zero**. Nothing extracted during a session is ever persisted, and every
launch re-extracts every icon from the shell.

Evidence: `%LOCALAPPDATA%\v3sper\launcher\icons.bin` is 12 bytes after a full day
of real use, and was still 12 bytes after three scripted sessions on 2026-08-27
that drew several dozen icons between them.

```
0000  54 4B 49 31  01 00 00 00  00 00 00 00     TKI1........
      ^ magic      ^ version 1  ^ count 0
```

This matters beyond C5. ROADMAP v0.2 justifies having no application cache partly
with "the expensive half is already persisted in `icons.bin`", and that sentence is
currently false.

**What would close it:** flush on a debounce after extraction, or at exit, or both.
`flush()` itself is correct — it merges the old blob with the new bytes and does the
temp-file-plus-rename dance properly. It is only ever called at the one moment there
is nothing to write.
