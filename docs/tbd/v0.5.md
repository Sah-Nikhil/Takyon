# v0.5 — what is not done

Clipboard history landed: capture, encryption, exclusions, retention, the `!v`
Mode and paste-back. What follows is outstanding, with the phase that owns each.

---

## 1. There is no UI for retention or the blocklist — **closed in v0.6**

**Done.** The Clipboard History page carries retention, the `!v` toggle and the
blocklist editor. `clip_retention_impact` finally has its caller: the
confirmation names the real count and says the rows are overwritten rather than
moved, so there is nothing to restore from. Cancelling changes nothing, which is
covered by a Playwright test rather than left to care.

The original report follows.

Both are reachable only through IPC commands and a hand-written SQLite row.
`clip_retention`, `clip_retention_impact`, `set_clip_retention` and `clip_clear`
exist and are tested; nothing calls them. The blocklist is one `INSERT` into
`settings.db`, exactly as aliases have been since v0.3.

`clip_retention_impact` exists specifically so v0.6's confirmation dialog can
name the real number — "permanently delete 4,312 clipboard items" — which the
ROADMAP already asks for. The count is available now; the dialog is not.

**Consequence today:** retention is one month for anyone who never edits the
database, and a user who wants `forever` cannot ask for it without SQLite.

## 2. The driver could paste into the wrong window — **fixed**

Recorded because it was found by running the thing, and because the fix is a
rule anyone extending a driver has to keep. `Send-Text` always checked the
foreground before typing; the individual key sends did not. A browser took the
foreground mid-run and `Enter` reached it instead of the Palette - paste-back
put a real URL into someone else's window, and a `Ctrl+A`/`Ctrl+C` readback
replaced the clipboard.

Every consequential key now goes through `Send-KeyTo` / `Send-ChordTo` (by
window) or `Send-ChordToPid` (by process, for the Notepad the script started and
never one the operator had open). A refused key is a SKIP, never a stray
keystroke. `scripts/verify-guard-keys.ps1` asserts zero keys are sent when the
target is not the foreground; it needs no build and runs in seconds.

Left unguarded on purpose: the global hotkey, which must fire whatever holds the
foreground, and `Escape`, which does nothing anywhere.

## 3. Nine verification steps still need a person — **v0.5**

[`../verify/v0.5.md`](../verify/v0.5.md) has 35 steps. **25 are driven and
confirmed** against the release build by
[`../../scripts/verify-drive-v0.5.ps1`](../../scripts/verify-drive-v0.5.ps1),
which runs it under an isolated `LOCALAPPDATA` so a verification pass never files
the operator's own clipboard into the real history.

What is left, and why none of it is a code change:

| Steps | Needs |
|---|---|
| X1, X2, X3 | A password manager, and a UAC credential box. **The phase's exit criterion.** |
| K3 | A second Windows account, to prove the DPAPI binding |
| P2 | An elevated window — and the UIAccess signature in §3, so it is expected to be refused |
| P5 | Pasting an older clip back and confirming it becomes newest |
| W1, W3, W4 | Alt+Tab, an hour of use, and a contended clipboard |
| B1 | `bun run bench`, which nothing in this phase should move |

The exit criterion — copy a password from a password manager, find no trace —
**is therefore still not claimed.** Everything around it now is: capture,
encryption at rest, the blocklist, retention, paste-back and the Bangless
exclusion have all been confirmed against the running product.

## 4. Paste-back over an elevated window has never been tried — **v1.0**

`SendInput` cannot reach a window at a higher integrity level without a UIAccess
signature, and the signature is still the outstanding v0.1 item
([`v0.1.md`](./v0.1.md)). Verification step P2 is written and expects a refusal.
Whether a refusal is *silent* — the clipboard loaded, nothing pasted, no
explanation — is untested and is the failure a user would report as "paste
sometimes does nothing".

## 5. Only text is captured — **post-V1**

`ClipKind` has one variant. Images and file lists are named in the plan as
arriving "behind the same rules", and the seam is in place (`ClipKind`,
`Paste::kind`), but neither is built. `docs/plans/post-v1.md` is the honest home
for them until someone asks.

## 6. The blocklist is cached at startup and never re-read — **closed in v0.6**

**Done.** The `Blocklist` is opened once and managed, so the settings editor and
the capture thread hold the same `Arc`. `add` and `remove` already reloaded the
cache after a write this process makes, so an entry added in the window applies
to the next copy rather than the next launch. A row inserted into SQLite by hand
while Takyon runs still needs a restart, and now nobody has to.

The original report follows.

`Blocklist::reload` runs after every write *this process* makes, so v0.6's editor
will work. A row inserted by hand while Takyon is running does not take effect
until restart, which is why verification steps X4 and X5 both say "restart".

## 7. The command list is one row, and Settings cannot reach it — **half closed in v0.6**

**Settings reaches it now.** `clip_bang` / `set_clip_bang`, `clip_retention` and
its impact count all have callers on the Clipboard History page, so none of them
is a hand-edited row any more.

**Still one row.** `sources/commands.rs` remains a `const` table with a single
entry, and the type filter on the history surface still filters one type because
`text` is all that is captured (§5, post-V1). Both wait on a second command and
a second clip kind rather than on a settings window.

The original report follows.

`sources/commands.rs` is a `const` table built for more than one entry, and holds
exactly one. Everything a v0.6 settings page would want is already reachable —
`clip_bang` / `set_clip_bang` toggle the Bang, `clip_retention` and its impact
count exist — but nothing calls them, so both remain hand-edited rows in
`settings.db`. The type control on the history surface is likewise a real control
over one type: it filters, and there is only `text` to filter.

## 8. `bang.rs` arrived early and knows one Bang — **v0.9**

IMPLEMENTATION_PLAN §9 assigned Bang parsing to v0.9, and v0.5 task 7 needed
`!v`, so the parser is here now: position 0, ident to whitespace, unknown Bang
falls through to Bangless. What is *not* here is everything
`docs/plans/bang-registry.md` parks — the `!` picker, user-defined Bangs, aliases
between them, and the hint row an unknown Bang is supposed to show. A bare `!`
currently does nothing at all rather than opening a picker.

## 9. Search decrypts up to 5,000 rows per keystroke — **v0.7 or later**

`SEARCH_WINDOW` bounds the work because matching requires decryption, and nothing
else can bound it. On this machine's history that is far below the limit and the
cost is unmeasured. `!v` is not on the 30 ms Bangless budget, so this is a
latency question rather than a correctness one — but the number was chosen, not
measured, and a history that reaches five figures will make older clips
unfindable by search while still listing them.

## 10. `v0_3_a_fresh_pipeline_ranks_by_what_an_earlier_one_learned` flaked once — **v0.5**

Failed once during this phase's full-suite run and passed on every run before and
after, including in isolation. It uses a **fixed** temp directory
(`%TEMP%\takyon-pipeline-restart`) rather than `common::TempDir`, so any second
process running the lib tests would clobber it. Predates v0.5 and is unrelated to
clipboard work, but it is a test that can fail without a bug, which is worse than
no test.

## Not open

**A command that opens clipboard history is Bangless; a clip is not.** The line
ADR-0006 draws is around clipboard *content*, and the command row carries none.
Reading the rule as "nothing clipboard-related may be Bangless" would have left
the feature reachable only by a Bang nobody discovers.

**Clips are not a Source, and never will be.** `ClipStore` deliberately does not
implement the `Source` trait, so the guarantee that a Clip cannot appear in a
Bangless list is structural rather than a filter someone can forget (ADR-0006).
Two tests and one Playwright assertion cover it. This is a decision, not a gap.

**Field-level encryption, not SQLCipher.** ADR-0008 settled it, including the
metadata leak it accepts. Don't re-derive it.

**No Frecency on clips.** History is ordered by recency because that is what
"clipboard history" means. A usage lift would fight the ordering that makes the
list readable.
