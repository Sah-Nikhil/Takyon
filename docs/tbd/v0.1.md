## 1. The UIAccess helper has no real certificate

**Owner: v1.0.** A shipping blocker, not a v0.1 one.

The helper crate, the `uiAccess="true"` manifest, the named-pipe protocol and
`scripts/dev-sign-uiaccess.ps1` all exist and work against a **self-signed**
certificate. What has never happened: signing with a real certificate, installing
to a trusted location, and confirming the Palette appears over an elevated window.

Until then the Palette will not show above an elevated terminal. Observed on every
run of the v0.2 build:

```
[takyon] the UIAccess helper ... would not start: The requested operation
requires elevation. (os error 740)
```

That message is the helper refusing to launch unsigned, which is the system
working as designed rather than a defect.

Detail and the signing requirements:
[`../plans/uiaccess-signing.md`](../plans/uiaccess-signing.md).

**What would close it:** a code-signing certificate, an elevated PowerShell run of
the signing script, and step I-whatever of the v0.1 manual script executed against
an elevated window.

## 3. A refused autostart write is silent — **closed in v0.6 slice 1**

**Owner: v0.6. Done.** `useApplied` in `settings/controls.tsx` wraps the write,
shows the error string beside the control, and refetches in a `finally` so the
switch settles on what the registry says rather than on what was clicked. The
rule generalised: every control in the window now takes its value from the
refetch, not from the click.

Tested rather than left to the manual script, which was the other half of the
problem — forcing this state on a real machine takes a group policy, so nobody
was going to. `api.mock.ts` can refuse a write on demand
(`__takyon_mock.failAutostart`), and two Playwright tests in `settings.spec.ts`
cover the refusal and the recovery. Manual step A4 in
[`../verify/v0.6.md`](../verify/v0.6.md) still exists, against the real registry.

The original report follows.

`Settings.tsx`'s `toggle` writes, then re-reads `isEnabled()` so the switch shows
what the OS actually says rather than what the user clicked. That half is right and
is required by [ADR-0015](../adr/0015-os-state-lives-in-the-os.md).

The missing half is the message. `enable()`/`disable()` can fail for reasons Takyon
cannot fix — group policy, a locked hive — and the call is awaited with no
`try`/`catch`, from a `void toggle()`. So a rejection skips the re-read entirely and
is swallowed by the floating promise. The checkbox is controlled, so it snaps back
on the next render and the user sees a switch that visibly refuses to move, with no
explanation anywhere.

Tesseract's ADR-0026 states the intended behaviour: report the error, *then*
refetch. Takyon does the refetch and not the report, which is the worse half to
have.

**What would close it:** wrap the write, surface the error string beside the
control, and refetch in a `finally` so the snap-back happens whether it threw or
not. Fold into v0.6's Settings rewrite rather than patching the placeholder — the
window is being rebuilt anyway.

## 4. The `Run` value is written unquoted, and v1.0 moves the binary somewhere it matters

**Owner: v1.0.**

`auto-launch` 0.5.0 builds the registry value as
`format!("{} {}", app_path, args.join(" "))` — no quotes, and a trailing space when
there are no arguments, which is Takyon's case. This is upstream code, reached
through `tauri-plugin-autostart` 2.5.1, and not fixable where it is written.

It is inert today. The NSIS bundle installs per-user by default, to
`%LOCALAPPDATA%\Takyon`, and no component of that path contains a space.

**v1.0 changes that.** UIAccess requires the binary to sit in a trusted location, so
task 1 of [`../plans/v1.0-ship.md`](../plans/v1.0-ship.md) installs to
`C:\Program Files\Takyon` — the path `scripts/dev-sign-uiaccess.ps1` already uses.
The value then reads:

```
C:\Program Files\Takyon\takyon.exe
```

Windows still starts it, by the CreateProcess ambiguity heuristic: it tries
`C:\Program.exe`, then `C:\Program Files\Takyon.exe`, then the real path. So this is
a fragility rather than a defect — it depends on an undocumented fallback, and on no
file existing at either earlier interpretation.

**What would close it:** rewrite the value quoted immediately after every successful
`enable()`, including the one inside `self_heal_autostart`, which would otherwise
unquote it again at the next launch. `is_enabled()` only tests that the value
*exists*, never its contents, so a quoted value still reads as enabled and the
`StartupApproved` handling is untouched. One helper, called from the two places that
enable.

Tesseract carries the same latent bug and cannot act on it, because its install
location gives it no trigger. Takyon has a trigger, a date, and a known-cheap fix.
