# What v0.4 left undone

The calculator ships: arithmetic, percent, parens, exponent, a small function
whitelist, and offline conversion across length, mass, temperature, data and
time. Enter copies the answer. Both exit criteria are met.

Three things are open, and one of them is the phase's headline omission. Two more
were open when this file was written and were closed in the same session; they
are struck through below rather than deleted, because *how* they closed is the
useful part.

## 1. `2022` still takes the top row from Adobe Photoshop 2022

**What is undone.** In the default `automatic` Policy, a bare four-digit number
produces a Calc Entry, and `EntryKind::Calc` wins its tier outright — so the
answer sits above the application named after that year and holds Enter. Press
it and you get `2,022` on the clipboard instead of Photoshop.

**Why.** This is Raycast's own rule, adopted deliberately after watching it fail
this exact way in Raycast for Windows on this machine. A bare number answers only
when formatting changes it: `202` yields nothing because it is already written
the way we would write it, and `2024` yields `2,024` because it is not. The rule
is good — it is the reason three-digit and two-digit numbers are silent — and it
has no special case for years, because a year is just a four-digit number.

The escape hatch exists and is one switch away: **Settings → "Only calculate
after an = sign"** turns the whole thing off except for `=`-prefixed input, and
the Settings copy names this failure so the choice is informed.

**What would close it.** Either evidence from real use that the collision is
common enough to be worth a rule, or a rule that is honest rather than a hack. A
year-shaped exemption (1900–2100 yields nothing) is the tempting one and is worse
than it looks: it silently refuses to format the one range of numbers people
paste most often. A better version is probably ranking rather than detection —
letting a Calc Entry lose its outright tier when an application matches the query
*exactly* — but that touches `EntryKind::tier`, which is a wider change than this
phase should make on one anecdote.

**Owning phase: v0.6**, alongside the settings work that will own this switch
anyway. If real use never produces the collision, close it there as "measured, no
change".

## 2. Currency conversion is not built at all

**What is undone.** No currency unit, no rate source, no cache, no setting. `100
usd to inr` yields nothing, and so does every other currency pair. A unit test
asserts that `usd`, `inr`, `eur`, `gbp` and the spelled-out names resolve to no
unit, so the absence is enforced rather than incidental.

**Why.** The v0.4 plan required currency to be "Bang-gated or explicitly opt-in
with a default-off setting. Not both, and never neither." **At v0.4 neither gate
exists.** `bang.rs` is a v0.9 file and has not been written; there is no settings
store until v0.6, and the one preference the product has lives in the frontend's
`localStorage`. Building a third gating mechanism to hold one feature for two
phases would leave a settings store that v0.6 then has to migrate off.

Left out rather than half-built, because a rate fetch on the Bangless path is not
a performance problem — [ADR-0002](../adr/0002-bangless-queries-never-touch-the-network.md)
calls it a correctness bug, and the pipeline's "every Bangless Source is local"
test is the assertion that would have had to be weakened to ship it.

**What would close it.** v0.9's Bang registry, then currency as `!c`-style
Bang-gated conversion with a cached rate and a visible timestamp. The plan's
original warning still stands and should be carried across verbatim: *a stale
rate presented as current is worse than no rate.*

**Owning phase: v0.9.** The unit tables in `sources/calc/units.rs` are shaped for
it — adding a dimension is a table entry — but the rate source, the cache and the
timestamp are all new, and none of them belongs on the Bangless path.

## ~~3. Nothing has been measured against the performance budgets~~ — closed

**Closed 2026-09-01**, in the session that built the phase. `bun run bench
--alt-hotkey`, n=30, with four Sources in the fan-out:

| Budget | Measured | |
|---|---|---|
| Hotkey → first pixel, < 50 ms | p95 **24.7 ms** | PASS |
| Keystroke → first Entry, < 30 ms | p95 **16.4 ms** | PASS |
| Idle RSS warm, < 150 MB | **28.6 MB** across 7 processes | PASS |
| Process start → hotkey responsive, < 500 ms | **257.3 ms** | PASS |

The expectation held. The calculator does no IO, takes no lock on the query path
and allocates nothing beyond a token vector, and adding it to the fan-out did not
move the number it could have moved.

## ~~4. The calculator has never been used against a real clipboard~~ — closed

**Closed 2026-09-01.** Step C3 of [`docs/verify/v0.4.md`](../verify/v0.4.md) now
runs in the driver: it plants a sentinel on the clipboard, types `12*1.18` into
the release binary, presses Enter and reads the clipboard back. `14.16`.

Worth keeping the reason that assertion exists. The driver's first revision
injected shifted keys by hand and Shift silently did not take, so `12*1.18`
arrived as `1281.18` — which is a **valid expression**, so the Palette answered
1,281.18 and every screenshot looked like a pass. Only the clipboard read
disagreed. A verification script that photographs its own output can only catch
the failures that look like failures.

## 5. The Settings switch has not been exercised by a person

**What is undone.** F3-F8 of the verification script: ticking **Only calculate
after an = sign**, confirming the Palette stops answering on the next summon
without a restart, and confirming the choice survives quitting Takyon.

**Why.** The driver has no way to reach the Settings window's checkbox — it types
into the Palette and nothing else. The Playwright layer covers the same path in
the browser, including the `localStorage` write and the push across the seam, but
it cannot reach Rust, which is where the rule is actually enforced (TBC-0007).

**What would close it.** Eight steps, about two minutes, by hand.

**Owning phase: v0.4**, as part of the manual verification pass.

## Not open

Deliberate omissions, recorded so nobody re-litigates them:

- **No variables, no answer history (`ans * 2`), no date arithmetic, no bases or
  bitwise operators.** Out of scope for the phase, and each is a grammar
  extension rather than a bug. TBC-0011 names them as triggers that would send
  us to a crate rather than growing the parser.
- **Months and years are not time units.** Neither has a fixed length. Answering
  "3 months in days" with a number derived from 30.44 days invents precision.
- **`45+` is refused where Raycast answers 45.** Raycast is greedy on a
  half-typed expression to stop its row flickering while you type; the Stability
  rule already solves that here, so committing to a number the user has not
  finished writing buys nothing.
- **Data sizes are 1024-based.** Standards say `kB` is 1000; File Explorer says
  otherwise under the same label, and someone checking our answer against
  Explorer has to see the same number.
