# v0.7 — what is not done

File search landed: the walk, the memory-mapped index, watchers with overflow
handling, `!e`, the Bangless toggle, the Windows Search fallback, the roots editor
and the recents list Takyon owns. What follows is outstanding, with the phase that
owns each.

---

## 1. Mid-word matches do not rank — **closed in v0.7**

**Done.** `rank::score_path` adds a substring rung, `TIER_SUBSTRING`, below the
acronym rung and applied to File and Folder Kinds only. Applications keep the
tighter ladder, where a substring match on a long product name is noise.

The case that closed it: `!e FC 26` returned nothing for
`C:\GG\FitGirl\EA SPORTS FC 26`, because the name-prefix rung wants the start of
the whole name and the word-prefix rung compares whole words, so a phrase in the
middle cleared neither. It now returns both that folder and
`C:\FC 26 Live Editor`, prefix first. Floor of three characters, matching the
trigram floor, since two characters matched anywhere is most of an index.

The original report follows.

## 1a. Mid-word matches did not rank — the reasoning

**What is undone.** `!e config` finds `app.config.json`, because `config` is a
word prefix. `!e onfig` finds nothing, because the ladder in IMPLEMENTATION_PLAN
§3 has no substring rung — its rungs are exact name, keyword, name prefix, word
prefix, executable prefix and acronym.

**Why it is like that.** §5 says to verify trigram candidates "with the real
matcher from §3", and file Entries deliberately use the same ladder applications
do, so a file and an app that match equally well score equally. The trigram index
*does* find the candidate — `index.candidates("onfig")` returns it — and the
matcher then rejects it. So this is a ranking decision, not an index limitation,
and it is one line to change.

**Why it might be wrong.** Applications are things you know the name of; files
often are not. People type fragments of filenames far more than they type
fragments of application names, so the ladder that is right for one may be wrong
for the other.

**What would close it.** Either a substring rung below `TIER_ACRONYM` used only
for File and Folder Kinds, or a decision that name-prefix matching is correct and
this note is wrong. Do not decide it blind — the trigger is a `!e` query that
returns nothing for a file the user can see in Explorer.

**Owner: v0.8**, alongside the bang-registry work, since that is when Mode-specific
behaviour is next being thought about.

## 2. File Entries carry no icon — **post-V1**

**What is undone.** Every file and folder Entry has `icon: None`, so the Palette
draws its Kind placeholder rather than the file-type icon Explorer would show.

**Why.** The Recents Source has done the same since v0.3, and §6's whole point is
that icon extraction is lazy and off the query path. Extracting per result on the
`!e` path would put `IShellItemImageFactory` on a 20 ms budget. Doing it properly
means keying `icons.bin` by *extension* rather than by target path, since every
`.md` file shares one icon — which is a different cache shape, not a small change.

**What would close it.** An extension-keyed icon path in `icons.rs`. Worth it if
the file list reads as visually flat in real use; not before.

**Owner: post-V1.**

## 3. The `Building { pct }` percentage is always zero

**What is undone.** `IndexStatus::Building` carries a `pct`, and nothing ever sets
it above zero. The Palette and the settings page both say "Building the file
index…" without a proportion.

**Why.** The walk does not know its own denominator until it has finished — that
is what a directory walk is. A real percentage needs either a cheap pre-pass
counting directories, or a guess from the previous generation's entry count.

**What would close it.** The previous generation's count is the honest cheap
answer and is already in the header, so a rebuild could report against it. A first
walk would still have nothing, which is exactly when the row is shown longest.

**Owner: v1.0**, and it is a polish item — the row is correct today, just coarse.

## 4. `docs/verify/v0.7.md` has not been run by a person

**What is undone.** The script exists and was written with the phase, but no
section has been driven by hand. W4 (watcher overflow under a large `git
checkout`) and S3 (the Windows Search fallback finding something outside the
roots) are the two that cannot be reached any other way.

**Why.** The automated suite covers the same mechanisms on temp trees, which is
not the same as covering them on a real disk under real load.

**What would close it.** One pass, with `scripts/verify-guard.ps1` first — an
installed Takyon swallows every summon and the build under test never runs. That
bit twice during this phase.

**Owner: v1.0**, with the rest of the verification suite.

## 5. The entry count sat close to TBC-0005's lower trigger — **closed in v0.7**

**Done, by removing the constraint rather than tuning it.** Default scope is now
every fixed drive: 309,802 entries, 2.3 s warm walk, 24.6 MB. The lower trigger no
longer applies. TBC-0005's second amendment carries the measurement and the new
triggers, which are an upper bound on size and a query worst case rather than a
lower bound on coverage.

The original report follows.

## 5a. The entry count under curated roots

**What is undone.** The real-roots measurement returned **26,844** entries.
TBC-0005 says under ~20k means the roots are so narrow the feature cannot justify
itself. That is not a failure, but it is closer to the floor than to the ~289k
reference point ADR-0007 measured Raycast at.

**Why it might be fine.** The exclusion list removes `node_modules`, `.git`,
`target`, `dist` and `build`, which in a directory of code repositories is most
files by volume and almost none by value.

**Why it might not.** `build` and `dist` are also ordinary directory names. An
exclusion that is right for a repository is wrong for a folder of design work.

**What would close it.** The live count in Settings is the instrument — turn one
exclusion off, watch the number, and decide with it in front of you. Not a code
change.

**Owner: v1.0**, or sooner if a `!e` query misses a file that demonstrably exists.
