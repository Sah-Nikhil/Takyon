## 1. The Recents Source returns nothing on this machine, and cannot be verified here

**Owner: v0.3 if the setting is changed; otherwise permanently blocked, like
Steam.**

Found 2026-08-28 by `v0_3_measure_the_real_recent_folder`, which is the only test
that exercises the COM read at all. It reported **0 shortcuts in 1 ms**.

The cause is not a defect:

```
%APPDATA%\Microsoft\Windows\Recent   →  2 items, 0 .lnk files
                                        (AutomaticDestinations, CustomDestinations)
HKCU\...\Explorer\Advanced\Start_TrackDocs = 0
```

`Start_TrackDocs = 0` is Windows' **"Show recently opened items in Start, Jump
Lists and File Explorer"**, switched off. With it off the shell stops writing
`.lnk` files into that folder, so there is nothing to read and the Source is
correctly empty.

**This is the right behaviour and worth stating as a rule.** The user told
Windows not to track recent documents. Reading them from somewhere else — the
jump-list databases in `AutomaticDestinations`, say — would be technically
possible and a straightforward violation of that intent. Takyon reads the shell's
own list and inherits the shell's answer, including "no".

**What would close it:** turning the setting on, opening a few documents, and
running section N of the verification script.

**Narrowed 2026-08-29.** `tests/recents_shell.rs` points `%APPDATA%` at a temp
tree and writes real shortcuts through `IShellLinkW`, so the shell's own writer
now feeds the shell's own reader. The Source, the COM read, the existence check
and the kind ordering are all exercised — the first time any of that had run.
What is still blocked is narrower and honest: whether *Windows* puts anything in
that folder on this machine. That remains a setting the user turned off.

**The other way out is recorded rather than argued about.**
[TBC-0010](../tbc/0010-takyon-owned-recents.md) proposes a recents list Takyon
keeps itself, from what passes through the Palette — no setting governs whether
we may remember our own history. It is worth nothing until v0.7 gives the Palette
files to open, so it is sequenced there rather than here.

**Worth considering before v1.0:** if the Source is empty, the Palette should
probably say nothing at all rather than silently contributing zero rows — but a
Source that explains its own emptiness is a UI question, and there is no surface
for it until v0.6.

## 2. A recently-opened folder can never appear

**Owner: v0.7**, which is where folder Entries start mattering anyway.

`lnk::read` drops any shortcut whose target is not a file — the existence check
ADR-0013 requires, written when the only caller was the Start Menu walk and every
target was an executable. Recents reuses that reader, so a shortcut pointing at a
*directory* is discarded.

The effect is that `recents::recent_from` classifies `EntryKind::Folder`
correctly and nothing can ever hand it one. The branch is honest but unreachable
from `discover`.

**What would close it:** a reader that accepts directories, either as a second
function or as a flag on the existing one.

**No longer written blind.** In `tests/recents_shell.rs`,
`v0_3_a_recently_opened_folder_never_reaches_the_palette` builds a shortcut to a
real directory and asserts nothing arrives, so the gap is demonstrated rather
than deduced from reading `lnk::read`. The test goes red the day it is fixed,
and its failure message says so.

## 3. Aliases have no editor

**Owner: v0.6**, as planned rather than as an oversight.

`AliasStore` and `AppSource::apply_aliases` work and are tested, and the apply is
deliberately in-place so a new alias needs no re-walk. What does not exist is any
way to *create* one except an `INSERT` by hand, which the verification script
spells out.

One consequence to carry into v0.6: nothing calls `apply_aliases` after startup
yet, so even a hand-written alias needs a restart. The function is ready for a
caller; there is no caller.

Verification steps A1 and A2 no longer need the restart or the hand-written
`INSERT` to be *checked*: `v0_3_an_alias_puts_its_target_first_in_the_real_list`
opens a real `settings.db`, aliases a real Entry, applies it to the real
application list and takes it away again. The missing piece is still the editor,
which is a UI, and still v0.6.

## 4. The Stability lock has never been felt

**Owner: v0.3.**

Three unit tests cover the rule — a settled top holds, a new keystroke clears it,
and the list still reorders inside the delay. What none of them cover is the thing
it exists for: whether the top row *feels* still under your finger.

The plan asks for a deliberately slowed Source to make this observable, and that
does not exist. Without one, S1 in the verification script is a person staring at
a list that was probably never going to move anyway.

**What would close it:** a debug-only Source that answers after 300 ms, behind the
same kind of flag as the no-steal-focus one. Cheap, and it makes one of the
phase's headline guarantees demonstrable instead of asserted.

**Half of it closed 2026-08-29.**
`v0_3_a_settled_top_holds_against_the_real_clock` sleeps past `LOCK_DELAY_MS`
against the real index and then makes a rival genuinely outrank the top, so the
rule is now proven on the wall clock rather than on an injected `now_ms`. The
half that remains is the half the note was about: whether the top row *feels*
still under a finger. No test reaches that, and the slowed Source is still what
S1 wants.

## 6. `lnk::discover` depends on COM being initialised by somebody else

**Owner: v0.7**, which is the next phase to add a Source that walks shortcuts.

Found 2026-08-29 by a test that called it directly. On a thread with no
apartment it returns an empty `Vec`: 154 `.lnk` files on disk, zero read, no
error. `com::read` fails per shortcut and `None` from it is indistinguishable
from "not a launchable file", which is the whole reason it stays silent.

**Not a live bug.** Production reaches it only through `discover_all`, which
opens a `ComScope` first (`sources/apps.rs`). The hazard is the next caller: an
empty list looks exactly like a machine with no Start Menu, so this fails in the
one way nobody investigates.

**What would close it:** a `ComScope` inside `discover` itself. It is idempotent
by design — `RPC_E_CHANGED_MODE` is already treated as a working thread — so
nesting it inside the existing one costs nothing.

**There is no test for it**, deliberately. The trap only springs on a thread
that has not already run something else, and no test sharing a binary with
others can guarantee that. It was reproduced once, in isolation, and written
down here instead.

## 7. Duplicate handling — the learned-collapse feature, built then retired

**Owner: closed 2026-08-29.**

Task 1b shipped learned collapse (TBC-0008): two Entries with identical icons
that were each seen to start the same executable, twice, were merged and one row
hidden. It worked end to end — `ShellExecuteExW` with `SEE_MASK_NOCLOSEPROCESS`
returned a usable handle even for a `shell:AppsFolder\` AUMID, and the one
genuine duplicate on this machine (`Administrative Tools` / `Windows Tools` over
`control.exe`) corroborated and collapsed correctly.

It was **retired the same day**. The reason is the shape, not a bug: it can only
hide a duplicate *after* two learned launches, so a fresh machine shows both rows
until you have used each — counterintuitive, and something neither Raycast nor
PowerToys does ([`../prior-art/ranking-and-dedup.md`](../prior-art/ranking-and-dedup.md)).
The whole machinery is gone: `collapse.rs`, the `launched`/`collapsed` tables,
`collapses.txt`, `Frecency::merge`, `AppSource::apply_collapses`. `launch::open`
keeps returning the image path (`ShellExecuteExW`) — cheap, and reserved for
TBC-0010's owned-recents list.

The two duplicate cases that actually occur are handled by static rules that are
correct from first launch, no learning:

- **Fork under upstream's binary name** — the exe-stem gate (0.2.5): a row that
  matched only through its executable filename yields to any row that matched by
  name, so `chrome` no longer surfaces a fork's `chrome.exe`.
- **Bare `PATH` exe duplicating a shell app** — **fixed 2026-08-29.** A path
  match cannot catch it: File Explorer is an `AppsFolder` AUMID with no path. So
  `explorer` joins `calc`/`notepad` in `WINDOWS_DIR_APP_DUPLICATES`
  (`path.rs`) — Windows-dir exes the shell already lists as an app, dropped from
  the `PATH` walk. Curated, because the general rule cannot be written: matching
  a bare exe to a pathless AUMID has no key.

  **A larger noise finding sits behind it, left open.** The `PATH` walk surfaces
  **644 bare executables under `C:\Windows`** — `wuauclt`, `wmiprvse`,
  `xwizard`, `wsqmcons` and the like. They only appear on a near-exact stem query
  so they are latent rather than cluttering, but almost none is an app anyone
  launches. Raycast has none of them (it does not walk `PATH` for bare exes;
  `../prior-art/ranking-and-dedup.md`). A System32 noise filter is the real fix
  and is its own decision, not smuggled into the explorer change.

**Left on the user's machine:** the retired code created `launched` and
`collapsed` tables in `frecency.db` and a `collapses.txt`. Nothing reads them
now; they are dead. The one recorded collapse also merged `Administrative Tools`
usage into the `control.exe` row, which stays merged. Harmless, and cleanable by
dropping the two tables and the file — not done automatically, because it is the
user's data.

## 8. System entries — a curated catalog and a launch verb only half-proven

**Owner: v0.3 for the manual launch check; the catalog grows from use.**

Task 8 built the System Source: 35 curated `ms-settings:` pages and the 198
control-panel tasks walked from the All Tasks folder. Two things it leaves behind.

**The settings catalog is curated, not derived.** 35 pages hand-picked, keyed by
their stable `ms-settings:` slug with keyword aliases (`wifi` → Network). The
plan's open question — whether a fuller catalog can be *derived* rather than
hand-written — stays open, deliberately: Raycast's ~950 entries are almost
certainly a shipped table too. The slug is the durable half; the **title tracks
Windows' own copy and may drift** between versions, which is why matching leans on
the slug and keywords rather than the displayed title. Grow the table from use; a
derivation pass is a nice-to-have, not owed.

**The control-panel launch is proven only to bind.** An All Tasks item has no
reparseable name — it is positional (`::{ControlPanel}\0\…`), and every string
form of it was tested and none resolves through `SHParseDisplayName`. So the
item's absolute **PIDL** is captured at enumeration and launched by
`SEE_MASK_IDLIST`. `v0_3_control_panel_pidls_bind_for_launch` proves all sampled
PIDLs bind back through `SHCreateItemFromIDList` — the exact call the launch makes
short of `ShellExecuteEx`. What no test can prove is that the default verb then
*opens a window*: firing `ShellExecuteEx` in a test would launch the task for
real. **Verify §SY3 is the one manual step that closes this**, and unlike Steam or
Epic it is runnable on this machine — every control-panel task is present.

**Not a gap: the settings-URI half.** `ms-settings:` launches through the same
`ShellExecuteW` path as the Steam URL that already ships, so SY1/SY2 are low risk.
Only the PIDL path (SY3) is new ground.

## Not open — recorded to prevent re-litigation

- **`tauri-driver` is not being adopted.** Costed against this repository in
  [TBC-0007](../tbc/0007-visual-testing-approach.md), then re-examined on
  2026-08-29 once the alternatives were actually built. `verify-drive.ps1`
  already drives the real binary, the WebdriverIO service matches its driver
  against the Edge browser rather than the WebView2 Runtime, and it could not
  live inside `bun run test` without launching a window on every run. Rust
  integration tests and `tauri::test` reached further in an afternoon.
- **Recents are read on a timer, not per keystroke.** 20 seconds. A few hundred
  shortcuts through COM cannot happen inside a 20 ms query budget, and the
  measurement above (1 ms for an empty folder) says nothing about a full one.
