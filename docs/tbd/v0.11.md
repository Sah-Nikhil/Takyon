# v0.11 — to be done

What PATH hydration left behind, and who owns it.

## 1. The whole unix arm has never run — **v0.12**

`path_from_login_shell`, `path_from_launchctl`, `account_shell` and the
process-group kill compile for `aarch64-apple-darwin` under `bun run check:macos`
and have never executed. Every claim about them is reasoning from t3code's
`packages/shared/src/shell.ts` and from the shape of `getpwuid_r`, not from a
run.

The parts that are genuinely tested cross-platform are the pure ones — sentinel
extraction, merging, candidate ordering — because they parse unix-shaped data
whichever host runs the test. That was a deliberate change during the build:
both parsers originally used `std::path::MAIN_SEPARATOR` and `is_absolute`, and
both were wrong on Windows for data that is always unix. The tests caught it.

`docs/verify/v0.11.md` §B is the script. §9 (a `.zshrc` that reads from the tty)
is the one worth running first: it is the only check that exercises the timeout,
the process-group kill and the fall-through together.

## 2. `added` is usually 0 on a developer's Windows machine — **nothing**

Not a defect, and worth writing down before it is reported as one. Hydration
reports how many folders the inherited `PATH` did not have. On a machine where
Takyon was launched from a shell started after the last `PATH` edit, that number
is legitimately 0 and the line reads "the same set Takyon was launched with".

The mechanism was proven by running the ignored test under a deliberately
truncated two-entry `PATH`: 52 folders recovered, 50 new. A real 0 on a
Start-Menu launch means the login `PATH` was already current, which is the
common case on Windows and never the case on macOS.

## 3. A wrong `PATH` in the registry is copied faithfully — **nothing**

The Windows probe reads `HKCU\Environment` and the machine `Path` and trusts
them. A stale entry pointing at an uninstalled tool's folder is merged in and
walked, costing one failed `read_dir`. This matches what a new shell would do,
which is the point, but it means Takyon cannot be more correct than the registry.

## 4. A Windows version manager that lives in the profile is invisible — **post-v1**

Found by reading t3code's actual source after the build, rather than the plan's
summary of it. `resolveWindowsEnvironment` does not read the registry: it spawns
PowerShell with `-NoProfile -NonInteractive` and calls
`[Environment]::GetEnvironmentVariable()` — the same values Takyon reads
directly — and then does a **second pass**. If `node` does not resolve from that,
it re-runs with the profile loaded and captures FNM's variables.

That second pass is the case Takyon cannot see. `fnm` and nvm-for-Windows put
node on `PATH` from the PowerShell profile at each session start, never in
`HKCU\Environment`, so a `claude` installed under an fnm-managed Node is
unreachable here. `extra_dirs()` does not cover it either: the folder is a
version-stamped path under the manager's own root.

**Not fixed at v0.11 deliberately.** Loading a PowerShell profile is what the
plan rules out — it can be slow, can prompt and can print — and paying that cost
on every launch to serve a configuration nobody has reported using is the wrong
trade. The trigger to revisit is a real report of an Agent that a terminal finds
and Takyon does not. The cheap version, if it comes: run the profile pass **only
once, only after a probe has failed**, which is where `invalidate` already sits.

The unix arm has no equivalent gap — `-i` sources the rc files, which is exactly
where `nvm`, `asdf` and `mise` install themselves.

## 5. No `PATH` change notification — **post-v1**

`WM_SETTINGCHANGE` with `lParam` of `"Environment"` is how Explorer learns the
`PATH` moved, and Takyon does not listen for it. Re-hydration is driven by a
failed probe instead, which covers the case that matters (an Agent installed
mid-session) at the cost of one wasted probe. A watcher would make it
immediate and is not worth a message-only window before v1.0.

The unix side has no equivalent to miss: nothing broadcasts a `.zshrc` edit.

## 6. Row 2 does not re-walk after hydration — **v0.13**

`sources/apps/path.rs::discover()` reads the hydrated `PATH`, but the application
walk runs once at startup on its own thread, and hydration finishes on the
deferred-init thread with no ordering between them. In practice the walk is the
slower of the two and reads the hydrated value; there is no guarantee of it.

A CLI installed after launch therefore needs a restart to appear as an Entry,
even though `!c` finds it immediately. v0.13 owns the index refresh that would
fix this properly; a re-walk triggered by hydration completing would be the
cheap version.

## 7. `strip_ansi` handles two escape forms, not all of them — **nothing**

CSI and OSC, which is what a themed prompt emits. A shell that emits DCS, or a
raw `\r` overwriting the line, would leak into the candidate. The sentinel parse
also requires a `/` in the line, so garbage without one is rejected rather than
returned — the failure mode is "no `PATH` found", not "a corrupt `PATH` used".
