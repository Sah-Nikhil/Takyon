# v0.3 manual verification

Ranking that learns, and the Sources it ranks. Written as the phase is built, one
section per task, so nothing is improvised at the end.

Run [`../../scripts/verify-guard.ps1`](../../scripts/verify-guard.ps1) first,
every time. An installed Takyon swallows every summon through
`tauri-plugin-single-instance` and the build under test never runs, silently. The
guard found and stopped one at `D:\Takyon\takyon.exe` on 2026-08-27.

`Alt+Space` is unavailable on the development machine (Raycast holds it), so every
step below assumes the `TAKYON_HOTKEY` override — `Ctrl+Alt+Shift+F9` is what the
drivers use.

nine by driver and T9 by hand. The evidence sits in
[`../tbd/v0.2.md`](../tbd/v0.2.md) §9 and §10, which this section closes.

| # | Step | Expected | Status |
|---|---|---|---|
| T1 | Type `developer` | Two rows: **Developer PowerShell for VS 2022** and **Developer Command Prompt for VS 2022**, each with its own shortcut icon | confirmed |
| T2 | Neither row says `Store app` | Both come from the `.lnk` walk now, with real paths | confirmed |
| T3 | Select either, press `Ctrl+K` | The **full** menu — Open, Run as administrator, Open file location, Copy path. They have files; v0.2 offered Open alone | confirmed |
| T4 | Type `explorer` | **File Explorer** first. Not "Windows Software Development Kit", which held that identity before task 0 | confirmed |
| T5 | Type `node` | No **"Uninstall Node.js"** row. It is filtered from the `.lnk` walk and used to return through `AppsFolder` | confirmed |
| T6 | Type `phot` | Photos and Adobe Photoshop 2022, **neither carrying a second line** — unique titles, nothing to disambiguate (ADR-0016) | confirmed |
| T7 | Draw some rows, wait two seconds, look at `%LOCALAPPDATA%\v3sper\launcher\icons.bin` | Larger than 12 bytes and growing. 245 KB after one session, 492 KB after a second | confirmed |
| T8 | Quit, relaunch, re-run the same query | Icons appear from the blob. `icons.bin` is not rewritten smaller | confirmed |
| T9 | Launch one of the `cmd.exe`-hosted prompts, then another | Both start, and they start **different** things. Nine shortcuts share that executable and the arguments are the application | confirmed by hand |
| T10 | Query enough rows to overflow eight | The scrollbar is a 4px inset thumb, no track, no stepper arrows. Stock Windows painted it white with arrows through v0.2 | confirmed |

**T9 was the only step needing a person** — it starts real console windows and
leaves them on the desktop, which is why no driver does it. Run by hand on
2026-08-28 and it behaves. An earlier revision of this file also listed T3 and
T8; both turned out to be drivable and are confirmed above.

T8's evidence: `icons.bin` read **733,964 bytes** before the run, and the same
after two launches with the same query. Unchanged is the pass — every icon the
query drew came from the blob, so nothing was extracted and nothing needed
flushing. Under v0.2 the file was 12 bytes and every launch re-extracted.

T9's risk is low rather than unknown: `launch.rs` passes `args` and
`working_dir` straight to `ShellExecuteW`, so the nine ids that differ by
argument start nine different things. What a person adds is confirming it with
their eyes.

### What proves T9 without launching anything

`cargo test --lib v0_2_measure_the_real_walk -- --ignored --nocapture` prints
every Entry whose id carries arguments. On this machine, 34 of them — nine on
`cmd.exe`, two on `javacpl.exe`, two on the x86 `powershell.exe`. Before task 0
each of those families was one Entry.

## R — Tasks 1 to 3: ranking that learns

The slice is store, decay, compose. Tasks 1 and 2 have no visible surface of
their own — a database nobody reads shows nothing — so every step here is really
a test of task 3.

| # | Step | Expected | Status |
|---|---|---|---|
| R1 | Launch Takyon, then look in `%LOCALAPPDATA%\v3sper\launcher\` | `frecency.db` exists, plus its `-wal` and `-shm` while running | confirmed |
| R2 | Type `code` on a machine that has never launched either | T3 Code (Alpha) first, Visual Studio Code second. This is the **cold** order and it is correct | confirmed in use |
| R3 | Launch something from the Palette, then read the `usage` table | One row: its `EntryId`, `kind=app`, `count=1`, `score=1` | confirmed |
| R4 | Select something, `Ctrl+K`, Copy path. Re-query | Order **unchanged**. Copying a path is not choosing an application | confirmed in use |
| R5 | Launch anything, quit Takyon, relaunch, query it again | Still ranked up. Usage outlived the process | covered by test |
| R6 | Type a query matching many applications | Still at most 12 Entries, 8 rows visible. The 64-wide shortlist is internal | unit-tested |

Confirmed in real use on 2026-08-28, against installed 0.2.2:

- **Cold order updates on first launch.** Selecting Tesseract put it above
  everything for its query, from a database that had never seen it.
- **Counts compound.** Launching Telegram more often than Tesseract put Telegram
  above it — the "how often" half of Frecency working across two Entries rather
  than just lifting one off zero.
- **Copy path teaches nothing**, as R4 requires.

**R5 is now covered by a test rather than by hand**, and it is worth saying why:
no browser could reach it. The visual suite mocks the Tauri bridge (TBC-0007), so
Frecency never executes there. But a second `Pipeline` over the same directory is
an ordinary Rust test —
`v0_3_a_fresh_pipeline_ranks_by_what_an_earlier_one_learned` — and it runs in
fifty milliseconds.

Both halves are therefore proven: the write persists (R3's row was read back by a
separate process after Takyon was killed) and a fresh Pipeline ranks by it.
Running R5 by hand is now confirmation rather than discovery, and still worth
doing once, because the test builds its `Pipeline` directly and does not exercise
the startup wiring in `lib.rs` that hands it the real data directory.

R1 and R3 were driven against the release build on 2026-08-28 **from a cold
start** — no `frecency.db` existed beforehand. Launching Character Map through
the Palette produced exactly one row:

```
c:\windows\system32\charmap.exe   kind=app  count=1  score=1
```

The first attempt read an empty table, and that was the **driver rather than the
code**: its Enter never landed. Worth recording, because "no row" looks exactly
like a broken write, and what separated the two was a screenshot showing whether
Character Map had actually started.

R2 is the case `docs/tbd/v0.2.md` §2 recorded and is worth running in that order:
seeing the wrong answer first is what makes the right one mean something.

**R2 and R3 are one-shot per machine.** Once the editor has been launched, the
cold order cannot be observed again without deleting `frecency.db`. That is the
honest way to reset it — there is no other state involved.

## S — Task 5: the Stability lock

The plan calls this "the phase". Its unit test exists (three of them), but the
thing it protects against is a *feel* — the top row moving between the moment you
read it and the moment you press Enter — so it also wants a person.

| # | Step | Expected | Status |
|---|---|---|---|
| S1 | Type a query, stop, wait ~200 ms, then watch for a second | The top row does not move. Anything arriving late appears below it | covered by test |
| S2 | Type quickly through several letters | Rows reorder freely as you go. The lock is about a *stopped* query, not a frozen first answer | unit-tested |
| S3 | Settle on a query, then press Enter without looking again | You launch what you read. This is the failure the lock exists for and the only way to feel it is to trust it | not run |

**S1 wants a deliberately slowed Source to be conclusive**, which does not exist
yet — the plan asks for one. What does exist as of 2026-08-29 is
`v0_3_a_settled_top_holds_against_the_real_clock` in
`apps/desktop/src-tauri/tests/integration.rs`: it sleeps past `LOCK_DELAY_MS`
against the real application index, then makes a rival genuinely outrank the
settled top, and asserts the top holds and the rival appends below.

That is the *rule* proven on the real clock rather than on an injected `now_ms`,
which is what the three unit tests use. It is not the *feel*, and S3 is still a
person — there is no way to automate trusting a row you did not look at twice.

## A — Task 6: aliases

**There is no editor until v0.6.** An alias is one statement against
`%LOCALAPPDATA%\v3sper\launcher\settings.db`:

```sql
INSERT INTO aliases (alias, target) VALUES ('ps', 'c:\...\photoshop.exe');
```

The target is the `EntryId`, which for a Win32 app is its lowercased executable
path — `Ctrl+K` → Copy path gives it to you exactly.

| # | Step | Expected | Status |
|---|---|---|---|
| A1 | Add the alias above, restart Takyon, type `ps` | Photoshop first, above anything merely *named* PS | covered by test |
| A2 | Delete the row, restart, type `ps` | Photoshop is back to wherever matching alone puts it | covered by test |

Restart is needed only because nothing calls `apply_aliases` after startup yet;
the function itself takes effect in place, which is what v0.6's editor will use.

**Both are covered as of 2026-08-29** by
`v0_3_an_alias_puts_its_target_first_in_the_real_list`, which opens a real
`settings.db`, aliases a real Entry to a string that matches nothing, applies it
to the real application list, then removes it and checks the row is gone. Running
A1 and A2 by hand is now confirmation of the wiring in `lib.rs` rather than
discovery, and still worth doing once for that reason.

## N — Task 7: Recents

> **Blocked on this machine.** `Start_TrackDocs = 0` — Windows' "Show recently
> opened items in Start, Jump Lists and File Explorer" is switched off, so the
> shell writes no `.lnk` files and the Source is correctly empty. Measured
> 2026-08-28: **0 shortcuts**. Turn the setting on and open a few documents
> before running any of these by hand. See [`../tbd/v0.3.md`](../tbd/v0.3.md) §1.
>
> The Source itself is no longer unexercised: the tests below build their own
> Recent folder rather than waiting for the shell to fill this one.

| # | Step | Expected | Status |
|---|---|---|---|
| N1 | Open a document in any application, wait ~20 s, then search part of its name | It appears, below every application that matches | covered by test |
| N2 | `Ctrl+K` on a recent file | Open, Open file location, Copy path. **No Run as administrator** — a `.docx` cannot be elevated | unit-tested |
| N3 | Enter on a recent file | It opens in its associated application | blocked |
| N4 | Search a word matching both an app and a document | The application is above, always, regardless of how much better the document matches | covered by test |
| N5 | Open a *folder*, then search for it | **Known not to work** — `lnk::read` drops non-file targets, so folders never arrive. tbd §2 | covered by test |

**Everything except N3 is covered as of 2026-08-29**, by
`apps/desktop/src-tauri/tests/recents_shell.rs`. It points `%APPDATA%` at a temp
tree, writes real shortcuts through `IShellLinkW` — the shell's own writer — and
reads them back through the same COM path the Source uses. That covers a
shortcut becoming a document Entry (N1), a document never outranking an
application (N4), a folder shortcut never arriving (N5), a shortcut whose target
has been deleted producing no row, and `desktop.ini` and the jump-list databases
being ignored.

What it cannot cover is whether *Windows* writes anything into that folder here,
which is the setting above, and N3, which starts a real application.

N1's twenty seconds is the refresh interval, not a bug: the Recent folder is read
on a timer rather than per keystroke, because a few hundred shortcuts through COM
would blow the 20 ms query budget many times over.

These are the shell's recents, so they include files opened by any application —
not only ones opened through Takyon.
