# v0.11 — manual verification

`PATH` hydration against a real environment. Run against an installed build, not
`bun run dev`: the whole phase exists because a process started from a shell has
a different `PATH` from one started by Explorer or `launchd`, and `bun run dev`
gives you the shell's.

Section A is Windows and can be run today. Section B is macOS and cannot be run
until v0.12 gives the crate somewhere to run — it is written now so that the day
a Mac exists, nobody has to reconstruct what should have been checked.

## What automation already covers

Do not re-do these by hand:

- Sentinel extraction against realistic shell noise, `PATH` merging and dedupe,
  login-shell candidate ordering, and the Settings sentence:
  `cargo test --lib shellenv`, `cargo test --lib path`, `bun test status`.
- The live environment, both platforms:
  `cargo test --test shell_env -- --ignored --nocapture`. Hydrates against the
  real registry or the real login shell, asserts the result is a superset of the
  inherited `PATH`, and prints what answered and how long it took. **Run this on
  each platform before a release.** It also runs the deep pass and prints its
  cost, which is the number §6's gating decision rests on.
- The Settings sentence drawing in every state: `bun run test:visual`.

What is left below needs a person and an environment that changed after login.

## A. Windows

### 1. The registry is what answers

1. Launch the installed build from the Start Menu, never from a terminal.
2. Open Settings → Agents.
3. Under "Ask `!c` with", read the grey line. It says **PATH read from the
   registry**, a folder count, and how many of those are new.
4. The count is plausible for this machine — dozens, not four, and not zero.

### 2. A `bun add -g` is found without a reboot

This is the exit criterion. It is the whole phase in one check.

1. Confirm `opencode` is **not** installed: Settings → Agents shows
   `opencode (\`opencode\`) was not found on PATH.`
   If it is installed, `bun remove -g opencode` first and press **Check again**.
2. Leave Takyon running. Do not restart it, do not sign out, do not reboot.
3. In a terminal, `bun add -g opencode`.
4. Back in Settings → Agents, press **Check again**.
5. **opencode is found**, with a version. The folder count on the grey line may
   have gone up by one.
6. Press the hotkey and type `!c` — opencode is offered.

### 3. The re-probe is what makes step 2 work

1. With opencode now installed, `bun remove -g opencode` while Takyon runs.
2. Settings → Agents, **Check again**. opencode reads as not found.
3. `bun add -g opencode` again, **Check again**. Found again, without a restart.

The second half is the one worth watching: an Agent that resolved and then did
not is what triggers re-hydration, so this path is exercised only after a loss.

### 4. Nothing moved onto the startup path

1. `bun run bench --alt-hotkey`.
2. All four budgets hold. In particular **login → hotkey responsive stays under
   500 ms**: hydration runs on the deferred-init thread, and a regression here
   means it did not.

### 5. A `PATH` executable installed after login is launchable

Row 2, which now reads the same hydrated value.

1. With Takyon running, `bun add -g <some CLI you do not have>` — `cowsay` will
   do.
2. Restart Takyon (the application walk is not re-run on a probe).
3. Press the hotkey, type the command's name. It appears as an Entry and launches.

### 6. The profile pass — **needs a machine with a version manager**

The one path no machine here can exercise. It needs **`fnm`** specifically, or
another manager that computes `PATH` per shell session from the PowerShell
profile. **nvm-for-Windows, Volta and scoop will not reproduce this** — each puts
a fixed directory on the `PATH` once at install, which the registry read already
sees, so the pass would correctly add nothing.

1. Install `fnm` and let it manage Node. Its line goes in `$PROFILE`:
   `fnm env --use-on-cd --shell powershell | Out-String | Invoke-Expression`.
   Confirm it works from a **new** terminal: `where.exe node` resolves.
2. Confirm the registry does **not** know about it: open `regedit` to
   `HKCU\Environment`, read `Path`. fnm's multishell folder is absent — it is
   stamped per session, which is the whole gap.
3. `npm i -g @anthropic-ai/claude-code` (or whichever Agent) under that Node.
4. Launch Takyon **from the Start Menu**. Settings → Agents.
5. The first probe finds nothing. Within a couple of seconds the grey line
   changes to **PATH read from the registry and your PowerShell profile**, and
   the folder count goes up.
6. **The Agent is found.** This is the assertion; everything above is setup.
7. Press **Check again**. The profile is *not* re-run — it is once per process —
   and the Agent stays found.
8. Restart Takyon. The first probe finds nothing again, and the pass runs again.
   One spawn per launch, only when nothing resolved, is the intended cost.

If step 5 never changes: check `Get-ExecutionPolicy`. A `Restricted` policy stops
the profile loading and the pass returns what the registry already had, silently.
That is a known limit, not a bug — `docs/tbd/v0.11.md` §4.

## B. macOS — **needs v0.12, never run**

Nothing in this section has been executed by anyone. The unix arm of
`shellenv.rs` compiles for `aarch64-apple-darwin` and has never spawned a shell.

### 7. Launched from Finder, not from a terminal

1. Build and install the `.app`. **Launch it from Finder or Spotlight.** A build
   started from a terminal inherits that terminal's `PATH` and proves nothing —
   this is the single easiest way to get a false pass here.
2. Settings → Agents. The grey line names a shell — `zsh` on a default install —
   not `launchctl`, and not "could not be read".
3. The folder count is well above four. Four means `launchd`'s inherited `PATH`
   was all that was found.

### 8. A Homebrew Agent is found

1. `brew install` or `bun add -g` one of the three Agent CLIs.
2. Launch from Finder. `!c` finds it, with a version.
3. Ask it something. **The Turn answers.** This is the step that catches a shim
   that resolved but cannot re-exec `node` — resolution succeeding is not the
   same as the Agent running.

### 9. A version manager is followed

Only if one is installed. This is the case `-i` exists for.

1. With `nvm`, `asdf` or `mise` managing Node, install an Agent CLI globally.
2. Launch from Finder. It is found.
3. Switch Node versions (`nvm use` another major). In Settings → Agents, press
   **Check again**. The Agent is found or lost consistently with what a terminal
   would say — not stale.

### 10. A hostile rc does not hang the app

1. Add `read -r _ < /dev/tty` to the top of `~/.zshrc`. This is the trap the
   whole timeout exists for.
2. Launch from Finder. The Palette opens normally and the hotkey works — the
   probe is on the deferred thread and cannot block either.
3. Within about five seconds, Settings → Agents settles. The line says the `PATH`
   could not be read, **or** names `launchctl`. It does not spin forever.
4. `ps` shows no orphaned `zsh` left behind. The probe kills its process group,
   not just the shell.
5. **Remove the line from `~/.zshrc`.**

### 11. Row 2 offers commands, not files

1. `ls -l /opt/homebrew/bin` and pick a non-executable file if there is one.
2. In the Palette, its name returns nothing.
3. An executable in the same directory does return an Entry, titled with its
   whole name — `python3.11`, not `python3`.

## What a failure here means

| Symptom | Where to look |
|---|---|
| "could not be read" on Windows | `registry_path` — `HKCU\Environment` has no `Path` value, which is possible on a fresh account |
| "could not be read" on macOS | every login shell failed. Run the shell by hand: `zsh -ilc 'printenv PATH'` |
| Folder count of exactly 4 on macOS | `launchctl` answered instead of a shell, or the app was launched from a terminal that had a bare `PATH` |
| Found in Settings, Turn fails to start | the child's `PATH`, not resolution — `probe::command`, not `probe::resolve` |
| Line never says "and your PowerShell profile" | either something resolved (the pass only runs when nothing did), or `Get-ExecutionPolicy` is `Restricted` |
| A console window flashes on the profile pass | `bare_command` lost its `CREATE_NO_WINDOW` |
| Login budget regressed | `hydrate()` is being called somewhere other than the deferred-init thread |
