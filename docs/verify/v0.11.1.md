# v0.11.1 — manual verification

Agents installed as npm `.cmd` shims, and Agent processes that die with the
Palette. Run against an installed build, never `bun run dev`: the whole point of
section C is what a real window's dismissal does to a real process tree.

Section A needs a machine whose Agents came from `npm i -g` — on this machine
they are all real executables, which is why the bug shipped. Section B is the
answer copy. Section C is driven by `scripts/verify-drive-v0.11.1.ps1`.

## What automation already covers

Do not re-do these by hand:

- Every driver's argv holds no line break and no prompt, and `turn_input` carries
  the prompt: `cargo test --lib agents`.
- A real `.cmd` Agent, 30,000 characters with `%PATH%`, quotes and `&|^` on
  stdin; a cancel, a `cancel_all` and a closed gate each emptying a Job Object;
  a shim whose runtime is missing reading as `launcherBroken`:
  `cargo test --test agents_cli`. These run on every Windows CI job.
- A real Turn through a forwarding `.cmd`, one per signed-in Agent:
  `cargo test --test agents_cli -- --ignored --nocapture`. Costs tokens.
- The failure copy for every reason: `bun test status`. The Palette drawing a
  broken launcher: `bun run test:visual`.

## A. An npm install — **needs the laptop**

The machine that reported this. Everything else is a reproduction of it.

1. `where.exe opencode` names a `.cmd` — `%APPDATA%\npm\opencode.cmd`. If it
   names an `.exe`, this section proves nothing; that is the case that already
   worked.
2. Summon the Palette. `!c who directed titanic`, Enter. It answers. Before
   v0.11.1 this was `Could not start opencode: batch file arguments are invalid`.
3. Ask a follow-up in the Chat Surface. It answers, resuming the same session.
4. `!s who directed titanic`, Enter. Sources appear, then a streamed answer with
   numbered citations.
5. Repeat 2 to 4 with each Agent first in Settings → Agents.
6. Paste a genuinely multi-line question into `!c` (Shift+Enter or a paste) and
   send it. It answers.

## B. Failure copy — **any machine**

Each of these needs a broken install rather than a fixture, which is why they are
here and not in `bun test`.

1. Rename `%APPDATA%\npm\node.exe`'s folder off `PATH`, or point a copy of a
   shim at a program that does not exist. `!c` then reads: *"<Agent>'s launcher
   needs a program that is not installed. Reinstall Node.js, then <Agent>."*,
   with `'node' is not recognized …` under it in a monospace line.
2. Rename the Agent's binary. `!c` reads *"<Agent> (`<binary>`) was not found on
   PATH."* and names it.
3. Sign the Agent out and ask. The Agent's own sentence is shown unedited — its
   words, not ours.

## C. Nothing survives dismissal — **driven**

`pwsh -File scripts/verify-drive-v0.11.1.ps1` after `bun run build`. Add
`-Search` to include an `!s` Turn, which leaves the machine. It takes the hotkey
`Ctrl+Alt+Shift+F9`, because `Alt+Space` belongs to Raycast on this machine.

What it does, five times: summon, ask a question long enough that the Agent is
still writing, list every process under Takyon that is not WebView2's, dismiss,
and list again. The second list must be empty.

| Step | Dismissal | Expect |
|---|---|---|
| C1 | the hotkey | mid-answer tree is non-empty, then empty |
| C2 | Escape twice | the same |
| C3 | clicking away (focus loss) | the same |
| C4 | the hotkey, during `!s` | the same, with `-Search` |
| C5 | `Stop-Process -Force` on Takyon | every process in the mid-answer tree is gone |

**Run on 2026-09-14 against the v0.11.0 release build: 0 failures, all five.** The
mid-answer tree each time was `opencode` plus the `opencode` and `git` processes
it starts, and each dismissal emptied it.

Two things the script has to get right, both learned by getting them wrong:

- **It polls for the Agent rather than sleeping.** A Turn can be over in eight
  seconds, and sampling on a timer then finds nothing to kill and reads as a pass.
- **Focus loss is driven by launching a window, not by activating one.**
  `SetForegroundWindow` and `AppActivate` are both refused to a background
  process while the Palette holds the foreground. A process that has just started
  is given the foreground by Windows itself.

C5 is the one no code of ours can do anything about: it is
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` alone (ADR-0033). **It has no unix
equivalent**, so on macOS C5 will fail and that is recorded, not fixed
(`docs/tbd/v0.11.md` §8).

By hand, once, to see it rather than read it: summon, `!c` a long question,
Enter, and while it is writing run

```powershell
Get-Process claude,codex,opencode,node -ErrorAction SilentlyContinue
```

Dismiss the Palette and run it again. The second run prints nothing.

## What a failure here means

| Symptom | Where to look |
|---|---|
| `batch file arguments are invalid` | something put the prompt back in argv — `turn_args`, and the unit test that forbids it |
| The Agent hangs, answering nothing | stdin was written and not closed — `probe::write_input` drops the handle |
| A Turn survives dismissal | `window::hide` no longer calls `Turns::set_visible(false)`, or it runs after `EVENT_HIDE` |
| Only `cmd.exe` dies | the child was resumed before `AssignProcessToJobObject` — `job::spawn`'s order |
| A Turn refuses to start at all | the visibility gate: `window::show` never opened it |
| The answer arrives twice over | Claude's `streamed` rule — a delta and the whole message both rendered |
| A typed question spawns a probe per keystroke | `Palette.tsx`'s `probing` ref — `ask` is a new object per keystroke |
