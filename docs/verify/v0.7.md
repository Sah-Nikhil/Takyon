# v0.7 manual verification

File search. Written as the phase is built, one section per slice.

**Three slices.** Section I covers the index and the query path (slice 1); W the
watchers, overflow and the status row (slice 2); E, S and H the `!e` Mode, the
settings page and the owned history (slice 3).

Run [`../../scripts/verify-guard.ps1`](../../scripts/verify-guard.ps1) first,
every time. An installed Takyon swallows every summon through
`tauri-plugin-single-instance` and the build under test never runs, silently.
This bit during the phase: the bench harness reported "the hotkey never
registered", which reads as a hotkey bug and was an installed copy holding the
mutex.

`Alt+Space` is unavailable on the development machine (Raycast holds it), so
every step below assumes the `TAKYON_HOTKEY` override — `Ctrl+Alt+Shift+F9` is
what the drivers use.

**Build with `bun run build`, never bare `cargo build --release`.** A cargo-only
release binary launches, registers the hotkey and shows a Palette with a
completely dead frontend. It fails in the one way that looks like a Rust bug, and
it bit twice in this phase, because `cargo test --release` leaves exactly such a
binary behind in `target\release\`.

## Why any of this is manual

Most of the phase is covered automatically and should not be re-checked by hand:

| Claim | Where it is tested |
|---|---|
| The walk reaches every depth, skips exclusions, never descends a junction | `index::walker` |
| The on-disk format round-trips; a truncated or foreign file is refused | `index::store` |
| Candidates are a superset and the real matcher decides | `index::live` |
| A short query is answered by a prefix scan, not declined | `index::live` |
| A created or deleted file reaches the index through the real watcher | `tests/index_disk.rs` |
| Overflow marks Stale **before** rescanning, and a failed rescan stays Stale | `index::live` |
| A scoped rescan keeps the other roots | `index::live` |
| `!e` searches files only, and ignores the Bangless setting | `query` |
| An empty `!e` lists what Takyon opened | `query`, `sources::files` |
| The owned list is chronological, capped, existence-checked and clearable | `frecency` |
| The settings page renders, counts and confirms | `settings.spec.ts` |

What is left needs a real disk, a real watcher under load, and a real Explorer.

## I — the index (slice 1)

**I1.** Delete `%LOCALAPPDATA%\v3sper\launcher\index\`, start Takyon, and summon
the Palette immediately. `!e` should say **Building the file index…** rather than
showing an empty list. An empty list means "no such file", which during the first
walk is exactly wrong.

**I2.** Wait for the walk, then open Settings → File Search. The roots should be
your fixed drives, and the entry count is the number TBC-0005's triggers are
stated in. Write it down. The reference is 309,802 on this machine.

- Over ~1.5M: the index is approaching the 150 MB ceiling.
- A cold first walk over 60 s: the scope is too wide for this disk.

**I3.** Restart Takyon. `!e` must answer immediately and the count must be the
same. **A re-walk at startup is a failure**, not a slow start — check the count
appears without the Building row.

**I4.** `!e` a filename you know exists, four or more levels deep inside a root.
It must be found. Then `!e` a two-letter folder name — `HH` if
`C:\Data\0Projects\Create\HH` still exists. Two characters take the prefix scan
rather than the trigram path, and that path is newer.

**I5.** With whole-drive scope there is little left outside the roots, so this
step now tests the *exclusions* instead: `!e` a filename you know sits inside a
`node_modules` or a `build` directory. It must return nothing. That is the honest
failure, and it is what the S3 fallback exists for.

## W — watchers and staleness (slice 2)

**W1.** With the Palette closed, create a file in an indexed folder. Within about
two seconds, `!e` its name and confirm it is found. This is the exit criterion
and it cannot be checked any other way — the automated version drives the same
path but on a temp tree.

**W2.** Delete that file. `!e` its name again: it must stop being returned. A
deleted file that still appears is how the user learns the feature lies.

**W3.** Rename it instead, and confirm the new name is found and the old is not.

**W4.** **Overflow.** Run a large `git checkout` or an `npm install` inside an
indexed root — something producing thousands of file events at once. While it
runs, type `!e` and watch for **Some changes were missed — rescanning**. It may
pass quickly; the point is that it appears rather than the index silently
carrying on. Afterwards, confirm a file created during the checkout is findable.

**W5.** Delete a **directory** containing several indexed files, then search for
one of them. It must be gone. Windows sends one event for the directory and none
for its contents, so this is a different code path from W2.

## E — the `!e` Mode (slice 3)

**E1.** `!e` with nothing after it lists what you have opened *through Takyon*,
newest first, files and folders only. On a fresh profile it is empty, which is
correct — open something through `!e` first, then check it appears.

**E2.** Open a file from `!e` with Enter. It must open in its default
application.

**E3.** `Ctrl+K` on a file Entry offers exactly **Open**, **Open file location**
and **Copy path** — no Run as administrator, which a document cannot do.

**E4.** Use Open file location. Explorer must open *with the file selected*, not
merely at its folder.

**E5.** Use Copy path, then paste. It must be the full path.

**E6.** Delete a file that is in the `!e` recents list, then type `!e` again. The
dead row must not be listed (ADR-0013's existence check).

## S — the settings page (slice 3)

**S1.** Settings → File Search. Add a root you know holds files — `C:\Data`, say.
The entry count must move upward within a walk's time, and `!e` must then find
something inside it that it could not find before.

**S2.** Remove that root again. The count must fall back and the file must stop
being found.

**S3.** **The fallback.** With a file outside every root in mind, confirm `!e`
finds nothing. Turn on **Also ask Windows Search** and repeat. Two things to
check, not one:

- the file is now found, *and*
- local results still come first when both have an answer.

If it is still not found, that is Windows' index, not ours — the same measurement
that put this toggle here found zero rows for `C:\Programming\SELF` on a machine
with the whole C: drive in scope. TBC-0005's amendment carries it.

**S4.** Add `node_modules` back as an exclusion if you removed it, and confirm the
count drops sharply. This is the cheapest proof that exclusions apply during the
walk rather than after it.

**S5.** Turn on **Show files without typing !e**. A Bangless query that matches
both an application and a file must show the application first, always. Turn it
off again and confirm file Entries disappear from Bangless results while `!e`
still works.

---

## H — the owned history (slice 3)

**H1.** Open two or three files through `!e`, then check `!e` with no query lists
them newest first.

**H2.** Settings → File Search → Clear history. The confirmation must name the
**real count**, not "some items".

**H3.** Confirm it. `!e` with no query must then be empty, and the files
themselves must still exist on disk — this deletes a record, not documents.

**H4.** Open something again and confirm the list starts refilling. A cleared
history that stays empty is a broken write, not a clean slate.

---

## Not open

These are decisions, not gaps, and should not be re-litigated here:

- **File Entries carry no icon.** The Recents Source has none either; extraction
  per file on the query path is what §6 exists to avoid.
- **Names only, never content.** Content search is Windows Search's job and it is
  behind the S3 toggle.
- **Mid-word matches do not rank.** `config` finds `app.config.json` by word
  prefix; `onfig` finds nothing. The ladder in §3 has no substring rung, and file
  Entries deliberately use the same ladder as applications.
